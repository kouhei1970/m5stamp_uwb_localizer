# 資料の格付けと実装方針 (2026-08-20 改訂)

## 経緯
Phase 2 では M5Stack 公式 Arduino ライブラリを「動作実績のある参照実装」とみなし、
**忠実移植**を方針としていた。しかしユーザ（M5Stack 製品に長い経験を持つ）の指摘により
この前提が崩れた:

> M5Stack のサンプルはいつもいい加減で、動かない場合も結構ある。
> この製品は出たばかりでユーザーもほとんど手にしておらず、実験結果が全く無い。
> Arduino 実装は無駄が多く、メーカのファームを徹底的に疑って批判的レビューをすべき。

**「参照実装は動く」という前提が無いなら、忠実移植は
(a) バグをそのまま持ち込み、(b)「原本通りだから正しいはず」という誤った安心を与える、
という最悪の組み合わせになる。**

実際、レビュー開始15分で重大な欠陥が2件出た（後述）。

### M5Stack 実装の位置づけ（重要）
- **`src/qm33120w_sdk/` は Qorvo のドライバそのもの → 一次資料 (P1〜P4)**

## 既に確定した M5Stack ラッパの欠陥

### 欠陥1: SS-TWR にクロックオフセット補正が無い【重大】
- `dwt_readclockoffset()` / `dwt_readcarrierintegrator()` は SDK に**存在するのに一度も呼ばれない**
- SS-TWR は開始側と応答側で別の水晶を使うため、折り返し時間 × 水晶偏差 のバイアスが出る
- 既定 `responseTxDelayUus = 3000` での誤差:
  | 水晶偏差 | 距離誤差 |
  |---|---|
  | 2 ppm | 0.9 m |
  | 10 ppm | 4.5 m |
  | 20 ppm | 9.0 m |
- **DS-TWR は原理的に免疫**があるため影響なし。
  M5Stack が謳う精度 0.14m は DS-TWR の値であり、辻褄は合っている
- → **SS-TWR は現状で使い物にならない**

### 欠陥2: ハードウェアのフレームフィルタが未設定【中〜重大】
- `dwt_setpanid()` / `dwt_setaddress16()` / `dwt_configureframefilter()` を一度も呼ばない
- チップは全フレームを受理し、アドレス照合はソフトウェアのみ
- 1対1のデモでは露見しないが、**アンカー5台の同時運用では他ペアのフレームが
  全部ホストまで上がる**。更新レートにも直接効く

### 誤検出だった例（記録として）
`dwt_rxreset()` が呼ばれていないことを疑ったが、**この SDK には存在しない**
（DW1000 世代の API）。**SDK ヘッダを根拠にせず憶測で指摘すると間違える**という実例。

## 実装方針（改訂）

### 原則
1. **実装の根拠は一次資料に置く。** M5Stack のコードは「そういう書き方もある」という参考
2. **定数はコピーせず、導出する。** 遅延時間はフレームの air time から計算し、
   マージンの根拠を示す。M5Stack の 3000us をそのまま使わない
3. **SDK が提供する機能を使っていない箇所は、使わない理由を確認する。**
   フレームフィルタ、クロックオフセット、温度補償、CIA診断など
4. **疑わしい箇所は実機で検証できる形にする。** Kconfig で振れるようにし、
   成功率と誤差を同時にログする

### 何を残し、何を作り直すか
| 層 | 由来 | 方針 |
|---|---|---|
| `qm33120w_sdk` | Qorvo（一次） | **そのまま使う** |
| `uwb_port` | 自作 | そのまま（ハード抽象。SDK の要求通りに実装済み） |
| `uwb_qm33120` デバイス層 | M5Stack 由来（二次） | **一次資料と突き合わせて検証・修正**。構造は流用してよい |
| `uwb_qm33120` TWR 層 | M5Stack 由来（二次） | **Qorvo リファレンスに基づき作り直す**方向で評価 |
| `uwb_loc` | uwb_localizer（自作・検証済み） | そのまま |
| `uwb_ranging` | 自作 | そのまま |

**「作り直す」と決めるかは、批判的レビュー（実行中）と
一次資料の調査（実行中）の結果を見てから判断する。**
移植版は「動くかもしれない出発点」として保持し、捨てはしない。

### 忠実移植をやめることの意味
- Phase 2 の成果（`uwb_qm33120`）は**破棄しない**。ビルドは通っており、出発点にはなる
- ただし「原本と一致しているから正しい」という検収基準は**無効**
- 新しい検収基準: **一次資料に照らして正しいか**

## 追記 (2026-08-20): 自分が使うツールの返り値も一次資料ではない

M5Stack のコードを疑う訓練をしながら、**自分のツールの出力を検証せずに信じて3回間違えた。**

| # | 誤り | 原因 |
|---|---|---|
| 1 | 「フレームフィルタ未設定は欠陥」と断定 | 公式サンプルを確認せず。しかも公式 `.c` が非UTF-8で `grep` が黙って0件を返す罠に嵌まった |
| 2 | 「操作対象はこのMacのChrome」 | ブラウザAPIの `isLocal: true` を検証せず信用。**実際は別マシン（リモート接続元のホストPC）だった** |
| 3 | 「ホストPCで見えたのは同期履歴」 | 「このMacにファイルが無い」という**矛盾する直接証拠を握りながら**、フラグを疑わず辻褄合わせをした |
| 4 | 「5V を入れると壊れる」と根拠なく断定 | 仕様値と絶対定格を区別せず、回路を見ずに断定。結論（5V 不可）自体は正しかった（3V3 はチップ直結で動作上限 3.6V・絶対最大定格 4.0V）が、当初は公式の「DC 3.3V」の記載を絶対定格と読み違えただけで、回路構成やデータシートの裏付けが無かった。実物確認（パッド 2 のチップ直結）と QM33120W データシートで裏付け直した（2026-08-21） |

**3件とも同じ失敗: 二次的な指標を、直接証拠より優先した。**

### 運用ルール
1. **フラグ・メタデータより、直接観測できる事実を優先する。**
   「ファイルが存在するか」「そのバイト列が何か」を見る
2. **矛盾する証拠が出たら、辻褄を合わせず前提を疑う。**
   「ファイルが無い」のに「ローカルのはず」なら、後者が間違っている
3. **`grep` が0件を返したら、まずファイルが読めているかを疑う**（非UTF-8、binary 判定）
4. **入手した資料は独立な経路で再取得してハッシュ照合する**
   （実施済み: 主要6件すべて SHA-256 完全一致を確認）

### ブラウザ自動化について
本プロジェクトでは**以後一切使用しない**。今後の作業（ESP-IDF ビルド、実機書き込み、
ベンチ測定、測位検証）で必要にならない。Web 取得は `WebFetch` / `curl` に限定する。
サブエージェントに調査を任せる際も**取得手段を明示的に限定する**。
