# uwb_loc の数値計算コスト分析 (2026-08-19、静的解析)

実機未着のため実測はまだ。**コードを読んでの見積もり**。
`firmware/soltest` に `esp_timer_get_time()` 計測を仕込んであるので、実機で裏を取る。

## 前提
- 外部の行列ライブラリ（BLAS/LAPACK）は**使っていない**。
  `src/uwb_linalg.c` (197行) が自前の小密行列演算を持つだけ:
  部分ピボット付き LU、コレスキー、循環 Jacobi 固有値、`AᵀWA` / `AᵀWb`。最大 9x9
- 次元: `d`=3（3D）、Beck の `nq`=d+1=4、EKF の `nx`=nd×norder = **6（CV）or 9（CA）**
- **ESP32-S3 は単精度 FPU のみ。`double` はソフトウェアエミュレーション**（1演算 数十サイクル）
  → 下記の乗算回数の差がそのまま実行時間に効く

---

## 1. Gauss-Newton (Lv0/Lv1/Lv2 の本体) — **無駄なし**

- `uwb_ata_weighted(J, w, n, 3, H)` → JᵀWJ は O(n·9)。**必要な計算そのもの**
- 3x3 の `uwb_solve_lin` / `uwb_inverse` は一般 LU だが、
  3x3 では閉形式展開との差は数十 flops。誤差の範囲
- **ここをスカラー展開する価値はほぼ無い**

## 2. Beck GTRS の二分法 — **無駄あり（中）**

`beck_solve_y()` が `(G + λD) y = h - λf` を**毎回 4x4 の一般 LU で解き直している**
（`uwb_closed_form.c:112-121`）。

- 呼ばれる回数: lo探索 60 + hi探索 200 + 二分 200 + 最終 1 = **最悪 461 回**。
  ただし典型は「lo/hi は数回で決まり、二分が相対 1e-14 まで ≈ 47回」で **~50回**
- 各回: 16要素コピー + 4x4 LU + 前進後退代入 ≈ **53 flops**
- 典型 ~2,700 flops / 最悪 ~24,000 flops

### 構造的な無駄
**G と D は λ に依存せず固定**。標準手法は:
1. G = LLᵀ（**既にコレスキー済み** — `uwb_closed_form.c:176`）
2. S = L⁻¹DL⁻ᵀ の固有分解（**既に固有値は計算済み** — 同 197行、`lam_lo` を求めるため）
3. S = UΛUᵀ が手に入れば
   `(G + λD)⁻¹ = L⁻ᵀ U (I + λΛ)⁻¹ Uᵀ L⁻¹`
   で `(I + λΛ)⁻¹` は**対角** `diag(1/(1+λλᵢ))`
   → **各 λ の評価が 4回の除算 + 内積の完全スカラー演算**に落ちる（~12 flops）

つまり **必要な材料（コレスキーと固有分解）は既に計算しているのに、それを使わず毎回 LU をやり直している。**

**ただし障害が1つ**: `uwb_sym_eigvals()` は固有ベクトルを返さない。
実装のコメントに「固有ベクトルは要らない (Beck 法は最大固有値しか使わない)」と明記されている
（`uwb_linalg.c`）。Jacobi 法なので回転行列を累積すれば固有ベクトルは自然に得られる。
→ **`uwb_sym_eigvals` に V の累積を足す**のが前提条件。

**見込み**: 典型 2,700 → ~600 flops（初期の固有ベクトル累積コスト込みで実質 2〜3倍）

## 3. EKF predict — **無駄あり（大）**

`uwb_ekf.c:112-122`:
```c
tmp = F·P      // nx³
P   = tmp·Fᵀ   // nx³
```
- CA(nx=9): 2 × 729 = **1,458 乗算**
- CV(nx=6): 2 × 216 = **432 乗算**

**F は CV/CA モデルのブロック構造**（対角に I、上三角ブロックに dt·I / (dt²/2)·I）で、
非ゼロは高々 nx + nd·(norder-1)·... ＝ CA で **15個程度**。
`F·P` は「P の行ブロックを dt 倍してシフト加算」だけで **O(nx²)**。

**見込み**: CA で 1,458 → ~162 乗算（**約9倍**）

## 4. EKF update — **無駄あり（最大。ここが一番効く）**

`uwb_ekf.c:301-356`。**測距1本ごと**に走るので、アンカー5台なら ×5。

### (a) `h` の疎性を使っていない
```c
for (a = 0; a < nx; ++a) h[a] = 0;
for (a = 0; a < e->nd; ++a) h[a] = j3[a];   // 非ゼロは先頭 nd=3 個だけ
...
for (a = 0; a < nx; ++a) { for (b = 0; b < nx; ++b) acc += P[a*nx+b]*h[b]; ph[a]=acc; }
```
`Ph` に **nx²=81 乗算**。必要なのは **nx·nd=27**。**3倍の無駄**

### (b) Joseph 形式を素直に O(nx³) で書いている
```c
tmp = I - K hᵀ         // nx² 要素を構築
m1  = tmp · P          // nx³ = 729
P   = m1 · tmpᵀ + KRKᵀ // nx³ = 729
```
`I - K hᵀ` は**単位行列のランク1更新**。展開すると
```
P ← P - K(hᵀP) - (Ph)Kᵀ + K(hᵀPh)Kᵀ + K R Kᵀ
```
で**全部が外積 = O(nx²)**。しかも `hᵀP = (Ph)ᵀ`（P は対称）なので使い回せる。

**Joseph 形式は数値安定性のために意図的に選ばれている**（コード中コメントに明記）。
上の展開は**同じ Joseph 形式のまま** O(nx²) にする書き換えであり、
数値的性質は損なわれない。

**見込み（CA, nx=9）**: 1測距あたり ~1,720 → ~300 乗算（**約5.7倍**）
アンカー5台なら 8,600 → 1,500

## 別軸: `UWB_USE_FLOAT`
ESP32-S3 は単精度 FPU を持つので、`double` → `float` は
**上記すべてを横断して効く可能性が高い**（ソフトエミュレーション → ハードウェア）。
ただし取り込み元 README が
「Beck法の二分法と共分散が単精度で桁落ちしやすいので、まず double で検証してから」
と警告している。**精度検証が先。**

## 4. 【重要】この測定はホストのもの

ESP32-S3 は **単精度 FPU のみ**。`double` の四則も `sqrt` も**ソフトウェア**。
したがって実機では:
- 乗算・除算の削減効果が**ホストより大きく**出る
- **`sqrt` のコストがホストの数十倍**になり、`uwb_evaluate` の 4N 回の sqrt が
  相対的に重くなる（ホストでは 0.0021us で無視できる）
- Jacobi の 1回転あたり sqrt 2回も同様に重くなる
  → **固有分解の相対比率はホストより更に上がる可能性が高い**

**深掘りは実機で測り直してから判断すべき。** `firmware/soltest` に計測を仕込んである。

また **`UWB_USE_FLOAT`（ハードウェア FPU + `sqrt.s` 命令）は、
上記のどの個別最適化よりも効く可能性が高い**。精度検証を先に済ませること。

## 最適化 D（安全策付きニュートン法）
- 括り出し（lo/hi 探索）は無改造で維持。二分ループのみ rtsafe 型に置換
- **反復回数 56回 → 3〜5回**

## 最適化 E（丸め誤差の床での打ち切り）
D の後、N=6/8 で「ニュートンは3〜5回で二次収束しているのに、
収束判定を満たすまで**二分を26〜31回も回していた**」ことが判明。
原因は `hi - lo < 1e-14 * max(hi, 1)` が
**λ ≤ 1 または負のとき実質「絶対許容 1e-14」**になること（純粋二分法の頃からの性質）。
- φ の桁落ちスケール `Σ(|μ_i z_i^2| + 2|g_i z_i|)` を使い
  `|φ| <= 8 * UWB_REAL_EPS * scale` で打ち切り
- 区間幅判定を `1e-14 * max(|lo|, |hi|, 1)` に修正
- 結果: **N=6 は 31→5、N=8 は 34→3 反復**。Beck が N によらず 0.79〜0.86us に揃った

### 【重要】E の実装中に潜在バグを発見・修正
最終的な `y` の復元が `beck_recover_y(&c, 0.5*(lo+hi), y)` になっていた。
**rtsafe は毎回 `lo`/`hi` の片方しか `x` に寄せない**ので、
収束を早めると `0.5*(lo+hi)` が遠い側の境界に引っ張られて不正確になる。
→ **最後に評価した `x` を使うよう修正**。
`UWB_USE_FLOAT` ビルドで `test_exact_when_noiseless` に **0.0945 m の誤差**が出ていた。
（純粋二分法では区間が十分詰まってから抜けるので顕在化しなかった。
  早期打ち切りを入れて初めて露呈するタイプ）

## 最適化 F（Jacobi の要素スキップ閾値）→ **差し戻した**
仕様通り実装し全テストは通ったが、**効果がゼロだった**ため差し戻した。

- 実測: `uwb_sym_eig` 4x4 = 0.5689（F前） → **0.5694（F後）**。同じ行列で誤差範囲
- 原因: Beck が扱う行列 `S = L^-1 D L^-T` (D = diag(1,1,1,0)) は
  **6つの非対角ペアすべてが均等に収束し、ちょうど4スイープで終わる**。
  「後半スイープで小さい要素が残る」というパターンが**この行列には存在しない**
  → 2000回のランダム試行でも**スキップ0回**
- 3x3（`uwb_anchors_coplanar`）ではむしろスイープが 3→4 に増えて**わずかに悪化**
- → 複雑さ（浮動小数の等値比較トリック）だけ増えて見返りが無いので**差し戻し**。
  C-1（固有ベクトル累積）は同じファイル内だが分離して残した

**教訓: 教科書的な最適化でも、対象の行列の性質次第では全く効かない。必ず測る。**

## 残る最大のコスト: Jacobi 固有分解 0.569us
Beck 0.79us のうち **72%** がこれ。`uwb_cholesky` 4x4 (0.025us) の**23倍**。
F では削れないことが分かったので、削るなら:
- **固有分解を廃止する設計変更**: ニュートン各反復で `(G+λD)` のコレスキー直接解、
  λ_max は power 法。φ' は `-2‖L^-1 w‖²`（w = Dy+f）で前進代入1回
  → 最適化 C の対角化を捨てることになる。**実機で測ってから判断すべき**
- あるいは Jacobi を Householder 三重対角化 + QL に置き換える

**ただしどちらも実機（ESP32-S3、double ソフトエミュレーション、sqrt ソフトウェア）で
測ってから判断すること。** ホストで最適な設計が実機で最適とは限らない。

## 付録: プラットフォーム側の高速化手段（旧 PLATFORM_TUNING.md）

この節は 2026-08-22 に `docs/PERF_ANALYSIS.md`（調査結果 2026-08-20）を統合したもの。

これまでアルゴリズム最適化ばかり見ていて、SDK/プラットフォームが提供する手段を
調べていなかった。その抜けを埋めた記録。すべて実際にツールチェーンで検証した事実。

### 1. 【最重要】ファームウェアが `-Og` でビルドされていた

```
CONFIG_COMPILER_OPTIMIZATION_DEBUG=y
→ 実際のコンパイルフラグ: -Og
```
（`build/compile_commands.json` で確認）

ホスト側のベンチはすべて `-O2`。**このまま実機で測っても比較にならない。**

- 対処: `CONFIG_COMPILER_OPTIMIZATION_PERF=y`（`-O2`）
- あわせて `CONFIG_COMPILER_OPTIMIZATION_ASSERTIONS_ENABLE` も見直す（現状 y、レベル2）

### 2. CPU が 160MHz（240MHz にできる）

```
CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ=160
```
ESP32-S3 は 240MHz 対応。**そのまま 1.5倍。**
- 対処: `CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y`
- 消費電力とのトレードオフ。StampFly のような電池駆動では要検討

### 3. 単精度 FMA `madd.s` / `msub.s` がハードウェアにある

**以前の調査で add/mul/div/sqrt しか見ておらず、FMA を見落としていた。**

| 命令 | 有無 |
|---|---|
| `madd.s` (float 積和) | **あり** |
| `msub.s` (float 積差) | **あり** |
| `madd.d` (double 積和) | **無し** |

しかも **GCC が `a + b*c` から自動的に `madd.s` を生成する**（-O2、ループ内でも
ハードウェア `loop` 命令と組み合わせて出る）。逆アセンブルで確認済み。

→ **`UWB_USE_FLOAT` の価値は、以前の見立てよりさらに高い。**
   EKF の P 更新や Gauss-Newton の JᵀWJ は積和の塊なので、
   float 化するだけで乗算+加算が1命令になる。

#### 改めて整理: ESP32-S3 の浮動小数点（すべて逆アセンブルで確認）
| 演算 | float | double |
|---|---|---|
| 加算 `add.s` / 乗算 `mul.s` | **ハード1命令** | ソフト (`__adddf3`/`__muldf3`) |
| **積和 `madd.s`** | **ハード1命令** | **無し** |
| 除算 | ソフト (`__divsf3`) | ソフト (`__divdf3`) |
| sqrt | ソフト (`sqrtf`) | ソフト (`sqrt`) |

`-ffast-math` でも除算・sqrt はハード命令にならない（ISA に無い）。

### 4. esp-dsp（Espressif 公式 DSP ライブラリ、v1.8.2）

`idf.py add-dependency "espressif/esp-dsp"` で取得できる managed component。

#### 関係しそうなもの
- **float 行列積の Xtensa アセンブリ最適化版があり、3x3 / 4x4 の専用実装まである**
  - `dspm_mult_3x3x3_f32_ae32.S`, `dspm_mult_4x4x4_f32_ae32.S`
  - `dspm_mult_3x3x1_f32_ae32.S`, `dspm_mult_4x4x1_f32_ae32.S`
  - `dspm_mult_f32_aes3.S`（S3 専用。`madd.s` を多用）
- float 内積: `dsps_dotprod_f32_aes3.S`
- 行列の加減・定数倍: `dspm_add/sub/addc/mulc_f32_ae32.S`
- **EKF モジュール**: `modules/kalman/ekf`（汎用EKF基底クラス、C++）
- sqrt: `dsps_sqrtf_f32_ansi()` — **ANSI 実装のみでアセンブリ版は無い**。
  近似による高速版の可能性があるが未評価

#### ただし適用範囲は限定的（重要な留保）
**我々の最適化後のホットパスは「単純な行列積」ではない**:
- EKF の P 更新 → ランク1更新（外積）。行列積ではない
- Gauss-Newton の JᵀWJ → 重み付き。素の行列積ではない
- Beck → 4x4 LU は既に廃止済み。いまはスカラー演算
- 3x3 の逆行列・連立解 → 行列積ではない

**皮肉だが、esp-dsp の行列積が最も効いたのは「最適化前の O(nx³) コード」**。
アルゴリズムを直した後では出番が減っている。
それでも `dspm_mult_3x3x3` / `4x4x4` が使える箇所がないか、実機測定後に再評価する価値はある。

#### 設計上の論点
`uwb_loc` は**依存ゼロの移植性重視 C99**（malloc も OS 依存も無い）。
esp-dsp を本体に入れるとその設計が壊れる。取るなら:
- マクロで切り替える optional backend にする、または
- `uwb_loc` は純粋なまま保ち、`m5stamp_uwb_localizer` 側のラッパで置き換える

### 5. ベクタ命令 (PIE) は測位計算に使えない

ESP32-S3 にはベクタ命令があるが**8/16bit 固定小数点専用**。
アセンブラで実際に確認:

| 命令 | 結果 |
|---|---|
| `ee.vmul.s8` / `ee.vmul.s16` | **あり** |
| `ee.vmulas.s16.accx` (積和) | **あり** |
| `ee.vld.128.ip` (128bitロード) | **あり** |
| `ee.vmul.s32` | **無し** |
| float 版 (`ee.vfmul.s` 等) | **無し** |

AI 推論向けの固定小数点 SIMD であり、浮動小数の測位計算には直接使えない。
使うなら測位計算全体を固定小数点化する必要があるが、
上流 README が float ですら桁落ちを警告している数値特性を考えると現実的でない。

### 6. RVfplib は使えない

`CONFIG_COMPILER_FLOAT_LIB_FROM_RVFPLIB` は `depends on ESP_ROM_HAS_RVFPLIB` で
**RISC-V 専用**。Xtensa の ESP32-S3 では選択できない。

### 7. その他の未評価項目
- **IRAM 配置** (`IRAM_ATTR`): ホット関数を flash から IRAM へ。
  flash キャッシュミスの影響を排除できる。命令キャッシュは現状 16KB/8way
- 命令キャッシュサイズの変更（現状 `CONFIG_ESP32S3_INSTRUCTION_CACHE_16KB`）
- flash 速度は既に 80MHz/DIO。QIO にできるかはボード依存
