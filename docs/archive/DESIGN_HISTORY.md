## 2. 廃案になった StampFly の配線案

採用されたのは「M5StampS3A 背面の 12P FPC を使う」案（`boards/stampfly.h`）。
そこへ至るまでに検討して捨てた案を記録しておく。

### 2.1 HW-1: GROVE 2系統4本を SPI に転用する

```
GROVE (RED  / I2C ): G13 = SDA → SCK,  G15 = SCL → MOSI
GROVE (BLACK/ UART): G1  = RX  → MISO, G2  = TX  → CS
```

半田付け不要で始められるのが利点だったが、次の問題を抱えていた。

- SPI 4本で GROVE を使い切るため **RST も IRQ も WAKEUP も取れない**。
  タグは常にポーリング（約31Hz）に固定される
- **GROVE のレールは StampFly では電池電圧そのもの**（満充電で約 4.35V）で、
  QM33120W の絶対最大定格 4.0V を超える。**LDO による降圧が必須**だった
- GROVE 2系統は基板上の別位置にあるため**カスタムケーブルが必須**
- GROVE を使い切るので他のセンサを増設できなくなる

採用案ではすべて解消した。特に電源は `VDD_3V3` が直接取れるので
**降圧回路そのものが不要**になった。

### 2.2 HW-2: 飛行系の SPI2_HOST に相乗りする

SPI 3線を M5StampS3A のキャステレーション、または基板上の SPI2 配線
（G44=SCK / G14=MOSI / G43=MISO）から分岐させ、空いた GROVE 4本を
CS / IRQ / RSTn / WAKEUP に回す案。IRQ と RST が取れるのが利点だった。

- **飛行制御の生命線である IMU (BMI270) と SPI バスを共有する。**
  UWB ドライバがバスをハングさせると IMU も止まる
- 実機で M5StampS3A のパッドに物理的にアクセスできるかが未確認のままだった
- 分岐のための半田付けが必要

採用案は **StampFly が1本も使っていない専有線（G16/G17/G18/G33〜G37）**だけで
完結し、飛行系の SPI2_HOST とバスを一切共有しない。

### 2.3 HW-3: 空き GPIO を使う → 不可能

StampFly の現行ファームが使っていない GPIO を転用しようとしたが、成立しなかった。
理由は §3.2 の訂正を参照。

**パターンは1つに集約される: 「二次的な指標を、直接証拠より優先した」「確認せずに断定した」。**

### 3.0 一覧

| # | 誤り | 正解 | 原因 |

以下は特に再発しやすいものの詳細。

### 3.1 半田パッド番号と FPC ピン番号は別体系

一時期「パッド番号と FPC ピン番号は同一」と書いていたが**誤り**だった。
公式回路図で確認したところ、キャステレーション（シンボル `PINMAP`）と
FPC コネクタ（シンボル `J1`）は**別のピン番号体系**であり、
**信号名は同一だが番号の並びが違う**。

- パッドは GND×3 (1/8/12)・VCC_3V3×1 (2)
- FPC は GND×2 (7/11)・VCC_3V3×2 (1/2)

本数からして違う。現在の対応表は `docs/WIRING.md` §2。

**この訂正は一度で終わらなかった。** 2026-08-21 に `SOLDER_PADS.md` §2 を直した
ときに `BRINGUP.md` の見出しが取り残され、翌日まで
「FPC ピン番号 = 半田パッド番号。固定」という誤記が残っていた。さらに
`PLAN.md` §3 にも「モジュール側（12P FPC、固定）」という見出しでパッド番号を
並べた一覧が残っていた。**同じ表を4つの文書に置いていたことが原因**であり、
これが配線表を `docs/WIRING.md` に一本化し、
`tools/docs_check/verify_docs.py` で機械的に検査するようにした直接の動機である。

### 3.2 G6 / G8 / G11 は IRQ の候補にならない

GROVE 構成を検討していた当時、StampFly の現行ファームが使っていない GPIO として
G1, G2, G6, G8, G11, G13, G15 の7本を挙げ、GROVE の4本以外に
G6 / G8 / G11 が未使用と考えたが、これは**誤り**だった。

**「ファームが使っていない」と「基板上でどこにも繋がっていない」は別の話**であり、
この3本はいずれも StampFly 基板上で IC に配線済みだった。

| GPIO | 基板上の接続先 |
|---|---|
| G6 | 底面 ToF (VL53L3CX) の INT |
| G8 | 前方 ToF (VL53L3CX) の INT |
| G11 | BMI270 の INT1 |

出典: `third_party/stampfly_ecosystem/firmware/vehicle/components/sf_hal_bmi270/docs/M5StamFly_spec_ja.md`。
コネクタには出ていないので、そのままでは転用できない。

**教訓**: フラグやメタデータ（「ファームが参照していない」）より、
直接観測できる事実（回路図・実配線）を優先する。

### 3.3 DW_RSTn への外付けプルアップは仕様違反

一時期「pin 6 (RSTn) ↔ pin 2 (3V3) 間に 10kΩ プルアップ」を保険として
推奨していたが**誤り**だった。QM33120W データシートは RSTn について
「Must not be pulled high by the external source」と明記しており、
High 側は IC 自身の POR 回路が駆動する。外付けプルアップは不要かつ仕様違反。

なおモジュール自体には R1 (10kΩ) + C15 (1µF) の RC が実装されている。
これは弱い抵抗プルアップであってホストによる能動的な High 駆動ではないので、
データシートの禁止事項とは矛盾しない。

### 3.4 IRQ 方針の変遷

当初は「タグのハードは StampFly 互換に保つ」という制約から、
**StampFly では IRQ 線が取れない**ことを理由にポーリング経路を第一級として
維持していた。IRQ は「使えるなら使う加点要素」の位置づけだった。

背面 12P FPC 経路の採用で**全ボードで IRQ が取れる**ようになり、
この前提が消えた。2026-08-22 に IRQ を既定（遅延プリセットも `BothIrq`）へ変更。

ポーリング経路自体は残してあるが、位置づけは**フォールバック**である。
残す理由は「IRQ の極性が実機未検証」「`pin_irq` を配線しない構成があり得る」
「ISR 登録に失敗しても測距だけは続けたい」の3点
（`docs/IRQ_POLICY.md`）。

### 3.5 「5V を入れると壊れる」を根拠なく断定していた

一時期この結論を、出典を示さずに書いていた（起源は
`docs/archive/SURVEY_m5stamp_uwb_module.md`）。
**結論（5V 不可）自体は正しかったが、根拠を示さないまま断定していたのが誤り**で、
後から公式回路図とデータシートで裏を取って初めて確定した
（パッド 2 は QM33120W の電源レールに直結、動作 2.4〜3.6V、絶対最大定格 4.0V）。

**教訓**: 安全に関わる結論ほど、正しくても出典を付ける。

### 3.6 「回路図の J1 シンボルが誤り」と判断しかけた

J1（FPC）のピン番号が PINMAP（パッド）と食い違うという事実だけを見て、
「公式回路図の J1 シンボルが間違っている」と判断しかけたが、**これは誤った判断**だった。
正しくは「J1 は FPC ケーブル用の番号、PINMAP はパッド用の番号で、**どちらも正しい**」。
§3.1 と同じ取り違えを、別の角度からもう一度やりかけたことになる。

### 3.7 `Uus` を `Us` にリネームしようとした

型名 `Uus` が実マイクロ秒ではなく UWB マイクロ秒（UUS）を指すことから、
当初「`Uus` → `Us` にリネームすべき」と判断したが**誤り**だった。
命名が誤っているのは Qorvo 側であり、M5Stack 由来の `Uus` という命名の方が正しい。
（経緯は [`REIMPL_PLAN.md`](REIMPL_PLAN.md) R1）

### 3.8 高さの実測では鏡像（キラリティ）は決まらない

自動測量の設計で、当初「反転あり/なしの両方を試し、高さ残差が小さい方を採用」と
書いたが**誤り**だった。高さモデルは線形汎関数なので、反転前後で実現できる
高さの組は完全に一致する。したがって高さからは掌性を検出できない。
現在は設置者にキラリティを入力してもらう設計になっている
（`docs/SURVEY_SPEC.md`）。

### 3.9 公式 PINMAP 画像・回路図 PDF の入手状況

`SOLDER_PADS.md` §1.7 は長らく「PINMAP 画像は配信サーバに接続できず取得できて
いない」「回路図 PDF は git 未追跡」としていたが、どちらも**既にリポジトリに
存在していた**（`assets/S017_Stamp_UWB_pinmap.jpg` と
`assets/SCH_UWB_MODULE_SCH_main_V0.2_...pdf`。後者は追跡済み）。
画像の内容は §2 の対応表と完全に一致していた。

## 4. 忠実移植をやめた経緯

Phase 2 では M5Stack 公式 Arduino ライブラリを「動作実績のある参照実装」とみなし
**忠実移植**を方針としていたが、ユーザ（M5Stack 製品に長い経験を持つ）の指摘で
前提が崩れた。

> M5Stack のサンプルはいつもいい加減で、動かない場合も結構ある。
> この製品は出たばかりでユーザーもほとんど手にしておらず、実験結果が全く無い。
> Arduino 実装は無駄が多く、メーカのファームを徹底的に疑って批判的レビューをすべき。

**「参照実装は動く」という前提が無いなら、忠実移植は (a) バグをそのまま持ち込み、
(b)「原本通りだから正しいはず」という誤った安心を与える、という最悪の組み合わせになる。**
以後「一次資料に照らして正しいか」を検収基準にした（現行の方針は `docs/PLAN.md`）。

### 当時 M5Stack ラッパに見つけた欠陥（どちらも決着済み）

**欠陥1: SS-TWR にクロックオフセット補正が無い**
`dwt_readclockoffset()` が SDK にあるのに一度も呼ばれていなかった。SS-TWR は
開始側と応答側で別の水晶を使うため、折返し時間 × 水晶偏差 のバイアスが出る
（`responseTxDelayUus = 3000` で 2ppm → 0.9m、10ppm → 4.5m、20ppm → 9.0m）。
DS-TWR は原理的に免疫があるので、M5Stack が謳う精度 0.14m（DS-TWR の値）とは辻褄が合う。
→ **本リポジトリでは実装済み**（`components/uwb_qm33120/src/uwb_qm33120_twr.cpp`）。

**欠陥2: ハードウェアのフレームフィルタが未設定** → **これは誤検出だった**（§3.0 の #1）。
Qorvo 公式 TWR の4例も使っていない。

**誤検出だった例（記録）**: `dwt_rxreset()` が呼ばれていないことを疑ったが、
**この SDK には存在しない**（DW1000 世代の API）。
SDK ヘッダを根拠にせず憶測で指摘すると間違えるという実例。
