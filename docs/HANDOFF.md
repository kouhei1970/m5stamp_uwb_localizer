## 0-D. 最優先: v2 アーキテクチャへの移行（2026-08-30 夜、実機検証済み）

`docs/ARCHITECTURE_V2.md` の設計を実装・実機検証した。§0-C で特定した欠陥（Poll 待ちの
200 ms 窓、Final 待ち中の Poll 取りこぼし）はいずれも**アンカーの構造そのもの**に起因して
いたため、Qorvo 例題直系の「1 本道のブロッキング関数」（`respondRange()` / `respondDSRange()`）
をやめ、**受信を常時 ON にしたステートマシン**へ作り直した。アンカーは新クラス
`uwb::Responder`（`components/uwb_qm33120/include/uwb_qm33120_responder.hpp`）が担い、
電波を扱う `uwb_radio` タスク（core 1・優先度 20）と、統計出力・コンソールなどの補助処理を
行う `main` タスク（core 0）を分離した。タグ側も同様に、測距・測位を独立タスク化した
`uwb::RangingService`（電波を扱う。core 1）と、ログ出力だけを行うロガータスク（core 0）に
分離した。PHY（データ速度・プリアンブル長・PLL 粗調整など）は新しい共通 Kconfig `UWB_PHY_*`
で `firmware/tag` / `firmware/anchor` 双方から選べるようにし、`firmware/twr` で得た 850 kbps
の知見を本番機に持ち込めるようにした。旧 `respondRange()` / `respondDSRange()` は当面
`firmware/twr`（A/B 比較用の実験ファーム）専用として残し、v2 が検証できた今、`firmware/twr`
のアンカー役も `Responder` に切り替えて旧関数を削除する作業が残っている（詳細は本節末尾）。

**W4R の空白（新たに見つかった欠陥、修正済み）**: 初版の `Responder` は、Response 送信
完了から W4R（wait-for-response）遅延 1500 UUS（≈1.5 ms）の間、受信を OFF にしたままに
していた。Response を受信エラーで落としたタグが即座に再試行の Poll を送ると、この空白に
落ちて失われていた（e51/e52 で `restarts` がほぼ 0 なのに 2 回目失敗率が 60〜68% と高いのが
その証拠——アンカーは再試行の Poll に気づいてすらいない）。**Response 送信直後に受信を開き、
W4R 遅延ぶんはタイムアウト（`rxTimeoutUus`）側に繰り入れる**修正（`ResponderConfig::listenImmediatelyAfterTx`）
を入れたところ、`restarts` が 212 に増え、2 回目失敗率は 28%（e55）まで下がった。残りは
再試行前の待ちを 2 ms にすると 15%（e57）、10 ms で 9%（e58b）——独立試行なら 8〜11% 程度
（1 回目の失敗率 8〜11% と同水準）まで下がる。

**本番タグの再試行待ちの既定を変更**: `UWB_TAG_RETRY_DELAY_MS` を DS-TWR でも 2 ms に
変更した（e57: 99.5%、周期時間 p95 17 ms）。10 ms（e58b）は成功率が誤差の範囲でしか
変わらず、周期時間だけ伸びる。

**負の距離（新たに見つかった不具合、暫定対策済み）**: e55（ポーリング）のタグ側の距離
5450 件中 3 件が 0.5 m 未満（最小 −14.979 m）だった。IRQ（e56〜e58b）では 0 件。監査した
結果、再開経路（再試行でやり直す経路）のタイムスタンプ・シーケンス番号（試行ごとに +1）の
整合に欠陥は見つからなかった。ポーリング経路だけで出ることから、RXFCG（フレーム受信完了・
CRC 良好を示す割り込みビット）直後、CIA（Channel Impulse response Analysis、到来時刻の
精密推定を行うチップ内部処理）が完了する前のタイムスタンプを読んでしまっている疑いがある
（**未証明**）。対策として、CIADONE（CIA 完了を示すステータスビット）を待つ処理（上限 1 ms）
と、距離の妥当性検査（−0.5〜500 m の範囲外なら Result を送らず `badDistance` カウンタに
計上するだけにする）を追加した。以後の実験で再発の有無を監視する。

**スタック空き**: `uwb_radio`（8192 バイトのうち 6.5 KB 空き）、`uwb_ranging_svc`（8192 の

### 6.8 Mbps の切り分けと本番既定の決定（§G）

`docs/ARCHITECTURE_V2.md` §6 の仮説 (a)〜(e) を実機で切り分けた（e50, e60〜e65、v2
アーキテクチャ、DS は再試行なし・60 秒・約 1.2 m・PLL 粗調整 0x23 固定）。

**表の見方**: アンカー・タグそれぞれの累積カウンタ（`anchor_stats` / タグの試行数）から、
電文ごとの到達率を 3 区間に分けて出している——「Poll→アンカー」= アンカーが受信した
Poll 数 ÷ タグの試行数（Poll がアンカーに届いた割合）、「Resp→Final」= アンカーが受信した
Final 数 ÷ アンカーが送った Response 数（タグが Response を受け取り、Final を送り返し、それが
アンカーに届くところまでを 1 つのホップとして扱った割合）、「Result→タグ」= タグが成功
（cycle success）と数えた回数 ÷ アンカーが送った Result 数（Result がタグに届いた割合）。
3 つを掛け合わせるとおおむね「素の p」に一致する（後述の例外を除く）。

### 新既定の最終確認と PLL 粗調整（G-2、e66, e67）

上の「決定」を実機に反映したビルドで最終確認したところ、**PLL（Phase-Locked Loop:
位相同期回路）の粗調整コードの選び方だけで成功率が 90% 台から 50% 台まで落ちる**、
新しい落とし穴が見つかった。条件: 850 kbps/256、`PollingBoth`、DS、再試行 2・待ち 2 ms、
IRQ、95 秒、約 1.2 m。

| # | PLL 粗調整 | 周期成功率 | 素の p | 2 回目失敗率 | 備考 |
|---|---|---:|---:|---:|---|
| e66 | チップの自動校正（Kconfig 0 = auto） | 86.8% | **50.1%** | 51% | 同条件で 0x23 固定の e56 は 99.0% / 90% |
| e67 | **OTP**（One-Time Programmable: 工場出荷時に書き込まれる個体固有の校正値。既定） の値で固定（`UWB_PHY_PLL_COARSE_MODE=OTP`） | **99.4%** | 90.5% | 14% | 起動ログ: 自動校正後 `pll_coarse=0x08001F24` → OTP（`otp_pll_cc=0x0B001F23`）の下位バイト `0x23` を強制 → `pll_coarse=0x08001F23`。両基板とも同じ |

- チップの自動校正は本日の温度（タグ 37〜39 ℃、アンカー 49〜51 ℃）で両基板とも `0x24`
  に落ち、OTP の工場値 `0x23` と 1 段ずれる。この 1 段だけで素の p が 90% → 50% に落ちる
  （§0-B「起動時温度で決まる状態」の記録と一致）。
- **対処**: 起動時に OTP アドレス `0x35`（PLL_CC）を読み、下位 7 ビットを
  `PLL_COARSE_CODE` に強制する `Qm33120::forcePllCoarseFromOtp()` を追加し、既定にした。
  ハードコード（`0x23`）ではなく個体ごとの OTP 値を使うので**基板が変わっても成立する
  （個体依存の値を都度読むので board-independent）**。OTP が未書き込み（0）なら安全弁と
  して自動校正のまま何もしない。本番ファームの起動ログに強制の前後 2 回、
  `Qm33120::logCal()` による `cal: pll_coarse=… pll_cfg=… pll_cal=… pll_status=…
  pll_lock=… otp_pll_cc=… xtal_reg=…` 行を追加した。

**最終の本番既定（Kconfig）**:
`UWB_PHY_DATA_RATE_850K` / `UWB_PHY_PREAMBLE_LEN=256` /
`UWB_PHY_PLL_COARSE_MODE_OTP`（新規、既定） / `UWB_TIMING_PROFILE_POLLING_BOTH` /
`UWB_ENABLE_IRQ=y` / `UWB_TAG_RETRY_MAX=2` / `UWB_TAG_RETRY_DELAY_MS=2`。

**このリポジトリを `pull` した直後は `sdkconfig` を削除して作り直すこと**
（`firmware/tag/sdkconfig` / `firmware/anchor/sdkconfig` は Git 管理外なので、
古い `sdkconfig` が残っていると上記の Kconfig 既定値変更が反映されない。
`docs/GETTING_STARTED.md` 参照）。

**結論**:
1. 本番既定の p=1% の主因は **`BothIrq` プリセット**（Response 878 / W4R 400 / Final 683 /
   W4R 200 / RX タイムアウト 1200 UUS——余裕が薄すぎる）である。同じ PHY（6.8 Mbps/128）で
   `PollingBoth` 相当の余裕あるプリセット（3000/1500/3000/1500/3000）にするだけで 40% まで
   上がる。IRQ とポーリングは無関係（e60 ≈ e61）。**§6 の仮説 (a)（IRQ 経路の遅れ）は棄却、
   仮説 (b)（`BothIrq` プリセットが詰まりすぎ）は確定**。
2. 6.8 Mbps ではプリアンブル長が効く: 128 → 40%、256 → 57%、1024 → 75%（**仮説 (d) 支持**。
   捕捉の問題が大きい）。ただし 1024 では 4 電文分の SHR（同期ヘッダ）だけで ≈4 ms 増え、
   周期 16 ms は 850 kbps/256・DS の 9 ms より遅い。**6.8 Mbps はこの機材では速度の利点が
   無い。**
3. タグ側の受信（Response・Result）がアンカー側（Poll）より一貫して悪いのは、主に**基板差**
   である: 役割を入れ替えると p が 57% → 70% に上がった（1101 側の基板の受信が弱い）。
   良い方の基板をタグにしても 850 kbps の水準（86.4%）には届かない。
4. **決定**: 本番既定を **850 kbps / プリアンブル 256 / `PollingBoth` タイミング /
   IRQ 有効 / 再試行 2 回・待ち 2 ms** にする。卓上で DS 99.5%（1 台 9 ms → 5 台 ≈45 ms、
   22 Hz）、SS 99.7%（1 台 6 ms → 5 台 ≈30 ms、33 Hz）。`BothIrq` / `AnchorIrq` の DS
   プリセットは 6.8 Mbps 用に導出されたものだが実機で p=1% だったため、**再導出するまで
   既定から外す**。PLL 粗調整は **OTP の値で固定（既定）**——チップの自動校正だと
   本日の温度で素の p が 90.5% → 50.1% まで落ちることが分かった（下記「新既定の最終確認と
   PLL 粗調整（G-2）」参照。§0-B の温度依存の記録とも一致）。
5. 残る 6.8 Mbps の手（未実施）: 距離 3〜5 m での受信飽和の確認、SFD（Start-of-Frame
   Delimiter）種別（IEEE 4z）の比較、DS の Result 電文を Response に相乗りさせて電文数を
   3 に減らす設計変更。

**e50 の掛け算チェックについての注記**: 上表の「3 つを掛け合わせるとおおむね素の p に一致する」
方法を e50 に当てはめると 0.75×0.11×0.38 ≈ 3.1% になり、実測の p=1.0% と約 3 倍食い違う
（他の 7 行は概ね ±1 ポイント以内で一致する）。`BothIrq` は余裕が最も薄いプリセットなので、
各区間の失敗が独立ではなく相関している可能性がある（1 区間で崩れるとタイミングがずれ、
続く区間も崩れやすくなる）という仮説はあるが**未検証**。

### EKF の更新方式（保留、2026-08-30 深夜にユーザーと議論）

一括（1 周 5 本を周の終わりに同時刻扱いで更新。現状）と逐次（距離 1 本ごとに、その時刻の状態に対して更新）を
シミュレーションで比較した（作業領域 `sim_ekf_batch_vs_seq.py`、5 台・DS 9 ms/台・σ 2 cm・欠測 10%・外れ値 0.5%）。
静止では両者等価（差 0.3%）。円運動では逐次が常に良く、実効遅れは一括 20〜23 ms に対し逐次 ≈0、位置 RMS の差は
1 m/s で 0.8 cm、2 m/s で 2.6 cm。差の内訳は「5 本を同時刻とみなす近似」（速いほど支配的、2 m/s で 8 割）と
「周の終わりまで待つ遅れ」。外れ値対策のイノベーション検定はどの方式でも必須。

**採用は保留**。方針: PX4 EKF2（遅延融合ホライズン + 出力予測器）は先行研究として参考にするが、StampFly では
より効率が良く独自性のある方法を考案または採用して違いを出す。候補:

1. 決定論的遅れの一次補正 —— TWR の交換時間は固定（測定の実効時刻 ≈ 結果到着の 4 ms 前）なので、
   $d' = d + (\mathbf{v}\cdot\mathbf{u})\,\tau$ で現在時刻に補正してから通常の更新にかける。バッファ不要、残差 $\tfrac12 a\tau^2$ は数十 µm。
2. Poll 時刻の状態複製（stochastic cloning）—— 交換ごとに Poll 送信時刻の位置 3 状態を複製し、結果到着時にそれへ更新して周辺化。厳密。
3. 推定器が測距順序を決める（能動測距）—— 共分散の最大方向を最も縮めるアンカーを次に選ぶ。欠測アンカーの再試行の無駄も消える。
4. 一斉測距プロトコル —— Poll 1 回の放送に各アンカーがスロットで応答、Final 1 回、Result をスロットで返す。5 台で 1 周 45 ms → ≈18 ms。
   v2 のアンカーはステートマシンなのでスロット応答を入れやすい。

共通の土台として、EKF の予測に IMU 加速度を入れる（等速モデルでは求心加速度 2.7 m/s² の旋回で検定が正しい測距を棄却して一時発散した）。

**本節で使う用語（初出順）**: RMARKER（測距基準点。タイムスタンプが打たれる時刻で、フレーム先頭ではなく
同期ヘッダの終わり）、SFD（Start-of-Frame Delimiter、プリアンブルの終わりを示す区切り。その終端が RMARKER）、
UUS（UWB マイクロ秒、1 UUS = 1.02564 µs）、tick（FreeRTOS の 1 ms 刻みの時計。ホスト側の待ち時間はこの刻みで
量子化される）、W4R（Wait-for-Response。送信完了後にチップが自動で受信に入るモード）、DX_TIME（遅延送信の予約
時刻レジスタ）、HPDWARN（Half-Period Delay Warning。予約時刻が半周期 8.6 s 以上先＝過去に回り込んだときに立つ
警告ビット）、PMSC_STATE（チップの電源・状態管理ステートマシンの現在状態。IDLE_RC = PLL 未ロックの待機、
IDLE = PLL ロック済み待機、TX、RX）、RX_FWTO（受信フレーム待ちタイムアウト。受信機を有効にしてからのハード側
タイマ）。「構造体のフィールド」はログ行の `key=value` の key と同じ名前なので、ログを読むときはそちらを見ればよい。

### 何が分かったか（要約）

SS-TWR が 99.95%（再試行込み）で通る同じ電波条件で DS-TWR が 0〜23% だった原因は、電波でも
チップでもなく、**DS 経路だけに入っていた構築上の欠陥 2 つ**である。

| # | 欠陥 | 生ログでの現れ方 | 根拠 |

| 1 | **タグの測距周期とアンカーの Poll 待ち窓が両方ちょうど 200 ms** で、窓の切り替わりの盲時間に Poll が落ち続ける「位相ロック」 | アンカーの Poll 待ち中の `RX_ERROR`（`elapsed_ms=194`）を境に、以後 `RX_TIMEOUT seq=0 elapsed_ms=200` が **200.0 ms 周期**で続き、タグは全サイクル `RX_TIMEOUT elapsed_ms=6` | `firmware/twr/main/main.cpp` の DS タグだけ `RANGE_INTERVAL_MS = 200` の即値（SS タグは Kconfig の 137 ms）。DS アンカーは `pollHostTimeoutMs` 既定 200 ms。e22 の時刻がミリ秒単位で一致 |

`rxRejected` が無く、ホストタイムアウト時は常に `RxTimeout` を返す）ため、何の証拠にもならない。

### 証拠 1: 位相ロック（e22、`DS_RESP_RET` を全呼び出しで記録したビルド）

生ログ: `/private/tmp/claude-501/-Users-kouhei-tmp-github-m5stamp-uwb-localizer/ecc50a4f-dd97-4381-937d-de776909a5b8/scratchpad/e22_ds_dbg_{anc,tag}.log`

アンカー Poll 待ち 200 ms / 両機 PLL 粗調整 0x23 固定 / 距離 1.03 m。

アンカー時系列（`I/W (ms)` はアンカーの起動からの時刻）:

```
2416 final_wait seq=10 elapsed=201 tx_margin=1996   ← Poll は窓の 194 ms に到着、Final 来ず (欠陥 2)
2816 final_wait seq=12 elapsed=201 tx_margin=2171
3609 RX_ERROR  seq=0  elapsed=194                   ← Poll が壊れて届いた。窓がここで終わる
3809 RX_TIMEOUT seq=0 elapsed=200 ┐
4009 RX_TIMEOUT seq=0 elapsed=200 │ 14 窓 = 2.8 s（不成立区間 3609→6511 は 2.9 s）、200.0 ms ちょうどの周期
 ...                              │ （201 は 1 つも混ざらない）。受信エラーすら無い
```

タグの CSEQ64（サイクルごとの成否、左が古い）: `0111111110101110000000000000001011011111111111111000000000000000` →
サイクル 10・12 = Final 待ち失敗、**16〜30 = 3609〜6409 の不成立期間（15 サイクル）**、31〜49 成功（32・35 は
Final 待ち失敗）、**50〜64 = 2 回目の不成立**。時刻の対応（タグの N サイクル目の Poll ≈ タグ時刻 615 + 200·(N−1) ms、
アンカー時刻 ≈ タグ時刻 − 6 ms）: 1 回目は **RX_ERROR 3609 = サイクル 16 の Poll** で、不成立の開始と一致。
2 回目は **RX_ERROR 10609 = サイクル 51 の Poll**（直前のサイクル 50 はアンカーに何の記録も無い＝プリアンブル
検出にも至らない普通の欠測。850 kbps の素の Poll 欠測率 3〜7% の範囲）で、51 以降が全滅。いずれも
「Poll 待ち中に RX_ERROR で窓が抜けた直後から、窓 200.0 ms 周期の空振りが続く」形になっている。

機構（コードから）:
- タグ: `if (nowMs() - lastRangeMs < 200) vTaskDelay(1); lastRangeMs = nowMs();` → 周期は 1 ms tick で
  量子化された **200.000 ms**。
- アンカー `respondDSRange()`: Poll 待ちは `dwt_setrxtimeout(0)`（ハード側タイムアウト無し）＋ホスト側
  200 ms ループ。ループを抜けるたびに `stopRadioAndClearRxStatus()`（`CMD_TXRXOFF`）→ return →
  次の呼び出しで `stopRadioAndClearIoStatus()` → PRETOC / rxaftertxdelay / rxtimeout の書き込み →
  `dwt_rxenable()`。この間 SPI 10 回前後（+ e22 ビルドは毎回 `ESP_LOGW`）＝ **数百 µs の盲時間**（SPI 1 回
  15〜30 µs からの見積り。オシロ等での実測はしていない）。
  850 kbps / 256 の Poll はプリアンブル+SFD が 269 µs しかないので、盲時間に頭が落ちると
  プリアンブル検出すらされない（RX_ERROR も出ない）。
- 窓の境界は「Poll 待ちループを抜けた時刻」で決まる。**Poll 待ち中に RX_ERROR で抜けると、窓の境界が
  Poll の到着時刻に再位相され、次の Poll は 200.000 ms 後 = 次の境界に落ちる。** 以後、両 MCU の
  tick の相対ずれ（数 ppm × 200 ms = 1 µs 未満/サイクル）でしか抜け出せない → 数十秒〜永久。
  成功交換や Final 待ちタイムアウトは Poll + 7 ms で抜けるので、次の Poll は窓の 193 ms に来て問題ない
  （裏付け: 交換の直後の窓で起きた Final 待ちタイムアウトが例外なく `elapsed_ms=201` = Poll 194 ms + ハード側
  RXFTO 7 ms。e21/e22/e23 の全 `stage=final_wait` 行がそう）。
- e16 / e18 / e24（最初から全滅）は起動時の位相がたまたま境界だった場合、または最初の Poll
  （アンカー起動中に届いて壊れる）で即ロックした場合。e17（22 サイクル後）/ e21（61 サイクル後）/
  e23（37 サイクル後）は最初の Poll 待ち RX_ERROR でロック。SS 実験（周期 137 ms）は毎サイクル
  位相が 63 ms ずれるのでロックが成立しない（e13: 20 交換ごとの記録に RX_ERROR は 0 件、99.95%）。

対立仮説の扱い:
- 「タグが送信していない」「アンカーの受信機が死んでいる」「PLL が外れた」は、**不成立期間が何も設定を変えずに
  アンカー側の RX イベント 1 つ（6511）で即座に終わり、直後のサイクルから成功率 90% 台に戻る**ことと両立
  しない（チップや RF の故障なら再位相で直らない）。PLL は両機とも粗調整 0x23 固定・`pll_lock=1` を起動時に
  確認済みで、同じタグが数秒前まで正常に送信している。ただし「盲時間の長さ」と「相対クロック偏差が
  1 µs/サイクル未満」は見積りであり、実測で確定させる（末尾の手順 3）。

### 証拠 2: Final の締切（DW3000 UM §9.4.1 エラッタ）

UM の原文（Version 1.1、Page 239）:
> "Due to an errata in the DW3000, there is a case when neither the HPDWARN event gets set nor does the
> packet get transmitted. ... the delayed send time must be set far enough in advance; it should be at least
> equal or more than the current time + preamble length + SFD length + 20 µs ... When this bug occurs, the
> PMSC_STATE will be "TX" but TX_STATE will be "IDLE", the TXFRS event will never be set. ... The host should
> abort the transmission in this case. This check and recovery is implemented in the published DW3000
> dwt_starttx() API."

- dw3000 用ドライバはこれを実装している（`assets/DW3_QM33_SDK_1.1.1/Drivers/API/Shared/dwt_uwb_driver/
  dw3000/dw3000_device.c:5253-5262`、`DW_SYS_STATE_TXERR 0xD0000`）。**本リポジトリが使う dw3720 用
  ドライバ（`components/qm33120w_sdk/dw3720/dw3720_device.c` `ull_starttx()`）には無い**（HPDWARN のみ）。
  QM33120W でこのエラッタが直っているかは一次資料に記載なし（未確認）。
- 850 kbps / preamble 256 のフレーム長（RMARKER 以後）: PHR 21.3 µs + データ (8·バイト数 + 48)×1.0256 µs
  → Poll(16 B) 0.20 ms / Response(24 B) 0.27 ms / Final(26 B) 0.28 ms / DWD(18 B) 0.22 ms。
  プリアンブル+SFD = 264 シンボル × 1.0176 µs = 0.269 ms。
- タグの Final 予約: Response の RMARKER を R として、フレーム終端 R+0.27 → ポーリング検出 0〜1 ms →
  タイムスタンプ読み出し・フレーム作成・SPI ≈0.25 ms → 予約時刻は **R+0.52〜1.52 ms**。締切は
  Final の DX_TIME (R+1800 UUS = R+1.846 ms) − (0.269 + 0.020) = **R+1.56 ms**。余裕 0.04〜1.04 ms。
  ポーリング遅延が最大側に振れたサイクル（観測では完了交換の 1.6〜15%）でエラッタ条件に入り、タグは `dwt_starttx()` 成功
  →（TXFRS も RX も来ない）→ ホストタイムアウト 10 ms → `forcetrxoff()`（PMSC=TX(0xD)>IDLE(3) なので
  `CMD_TXRXOFF` が出て回復）。アンカーは Final 待ちのハード側 RXFTO（Poll+7 ms）で抜ける →
  **`stage=final_wait` 行**。（比較: SS/DS の Response 予約は Poll の RMARKER + 3000 UUS で
  余裕 1.3〜2.3 ms。実測 `tx_margin_us=1568〜2300` と整合。）
- コードの `tx_margin_us` は「DX_TIME − 現在」であり、プリアンブル分（0.289 ms）を引いていない。
  正の値でもエラッタに入りうる。

### 一次資料で確定した SDK / チップの挙動（本節の前提。§0-B の記述を上書きする）

- `dwt_forcetrxoff()`（`ull_forcetrxoff()` dw3720_device.c:5821-5840）は `SYS_STATE_LO` の PMSC バイトが
  IDLE(3) 以下なら何もしない（IDLE_RC で `CMD_TXRXOFF` を出すと再起動が要る、と UM Page 238）。
  エラッタ状態は PMSC=0xD なので `CMD_TXRXOFF` は出る。
- 即時 TX（`CMD_TX`/`CMD_TX_W4R`）と即時 RX（`CMD_RX`）はチップ状態を見ず常に成功を返す。
  先行コマンド未完了時のファストコマンドは無視され `CMD_ERR` が立つ（UM Page ~157）。
- W4R の自動 RX は「送信完了」が条件。送信されなければ RX も RXFTO も起きない。
- RX_FWTO（受信待ちタイムアウト）は受信機有効化から走り続け、**フレーム受信中でも満了すると受信を
  打ち切る**（UM RX_FWTO の項）。受信窓はフレーム全体を覆う必要がある。
- HPDWARN は DX_TIME が半周期（8.6 s）以上先＝過去に回り込んだときだけ立つ。「近すぎる未来」は
  上記エラッタ。

### 実機で確定した結果（2026-08-30 実機セッション）

**読み方**: 本節は直前の節で立てた反証手順を実機で実行した記録である。共通条件は
M5StampS3A + M5Stamp UWB（QM33120W）2 台、距離 約 1.2 m 卓上（ユーザー申告。測距値は本日の全実験で平均 1.13〜1.15 m と一貫。本節で「1 m」と書いた箇所はすべてこの配置）、ch9、送信電力 0xFEFEFEFE、
PGdelay 0x34、PLL 粗調整 0x23 固定、IRQ 無効（ポーリング）、各 95 秒（タグ周期 137 ms なら
690 サイクル）。850 kbps 構成はプリアンブル 256 / PAC16（PAC: Preamble Acquisition Chunk、
受信機がプリアンブルを検出する際の相関窓の刻み幅。`docs/HANDOFF.md` 内で既出）。生ログの
在処は本項末尾。

|---|---|---|---:|---|---:|
| e25 | `tag_ds_dbg` | `anc_ds_dbg` | 137 | 受信継続（新方式） | 90.4%（624/690） |
| e26 | 同上（再測） | 同上 | 137 | 新方式 | 92.2%（636/690） |

| e29 | `tag_ds_i200` | `anc_ds_dbg` | 200 | 新方式 | 88.7%（417/470） |

e27（周期 200 ms **かつ** 旧方式）だけが 0% で、アンカーは Poll を 1 つも復号できず、
周期失敗ログ（20 件ごとに出る集計ログ）すら出なかった。周期 200 ms だけ（e29）、旧方式
だけ（e28）は単独では 88〜91% を維持しており、**「タグの測距周期がアンカーの Poll 待ち窓と
同じ 200 ms である」ことと「Poll の RX エラーで窓を再位相しない（旧 return 方式）」ことの
両方が揃わないと位相ロックは起きない**ことを実機で確定した。前セッションの e22（本節冒頭の
「証拠 1」、机上レビュー時点で唯一残っていた実測ログ）は 50 サイクル目からロックしたのに
対し、e27 は 1 サイクル目から（起動直後の Poll が窓の境界に落ちた）ロックした。

#### 反証 2（欠陥 2: Final の予約締切）

| # | タグ / アンカー | Final 予約 / 受信窓 / ホスト待ち（UUS/UUS/ms） | 周期成功率 |
|---|---|---|---:|
| e35 | `tag_ds_old` / `anc_ds_old`（旧プリセット忠実再現） | 1800 / 500 / 10 | 76.7%（529/690） |

e35 のうち 86 件（12.5%）が `stage=final_tx error=TX_START_FAILED`（TX_START_FAILED:
ドライバが遅延送信の起動時点でエラーを検出したことを示すエラー種別）で、`tx_margin_us`
（Final の遅延送信予約時刻まで残っている時間。負なら締切超過）は 196〜214 µs——これは
DW3000 UM（User Manual）§9.4.1 のエラッタ閾値「SHR（Synchronization Header、同期ヘッダ）
269 µs + 20 µs ≈ 289 µs」を下回っている。一方 `wedged`（今回追加した、チップの内部状態
レジスタ SYS_STATE_LO を直接読んで `0x000D0000` かどうかを見る検査。§0-C 証拠 2 が予想した
「HPDWARN も立たず送信もされない無警告の不成立」そのものを検出するために追加した）は
**全実験を通じて 0 件**だった。

**機構の訂正**: 証拠 2 は「HPDWARN も立たず送信もされない無警告の不成立」を主要な失敗経路
として想定し、頻度は 1.6〜15% と見積もっていた。実機ではこの頻度の見積り（12.5%）は的中
したが、**壊れ方は予測と異なっていた**。観測された 86 件は全て、`dwt_starttx()` 自身
（DW3720 用ドライバの `ull_starttx()`。HPDWARN のみを検査する）が HPDWARN 検査で送信開始を
拒否し `DWT_ERROR` を返す、通常の（無警告ではない）失敗経路であり、`abortIfDelayedTxWedged()`
（今回追加した、`dwt_starttx()` が成功を返したにもかかわらず実際には送信されていない場合を
捕捉する検査）は一度も発火しなかった。無警告の不送信エラッタそのものは今回の実機では
再現しなかった（QM33120W でこのエラッタ自体が直っているのか、今回の条件では踏まなかった
だけなのかは未確認）。

予約余裕（`tx_margin_us`）は二峰性だった: 通常は `finalTxDelayUus=1800` のとき ≈1081 µs、
`=3000` のとき ≈2312 µs。全サイクルの約 10〜12% で折返し（Response 受信からタグが Final
送信を起動するまで）に約 0.9 ms 余計にかかり、余裕がその分だけ薄くなる（e25 でも
`tx_margin_us=1441` が観測 46 行中 5 行に出ている）。折返し時間そのものに直すと通常
≈0.7 ms、遅い側は ≈1.6 ms——**この二峰性の原因は未確認**（§1.3 の見積り「ポーリング約
1.2 ms」の範囲には収まっている）。`finalTxDelayUus=1800` では遅い側の余裕が ≈200 µs まで
下がりエラッタ閾値 289 µs を割るため 12.5% が失敗する。`=3000` では遅い側でも ≈1430 µs で
閾値を大きく上回るため失敗しない（e25/e26/e28/e29/e36 に Final の TX_START_FAILED は
出ていない）。

#### e30: もう一つの設計ミス——受信窓の基準点の取り違え

| # | タグ / アンカー | Final 予約 / 受信窓 / ホスト待ち | 周期成功率 |
|---|---|---|---:|
| e30 | `tag_ds_f1800` / `anc_ds_dbg`（Final だけ 1800 に戻し、受信窓は新プリセット 1500 のまま） | 1800 / 1500 / 20 | **0.0%（0/690）** |

アンカーは `final_wait` 段の `RX_TIMEOUT`（RXFTO、受信フレーム待ちタイムアウト）が
681 件、タグの `tx_margin_us` は ≈1146 µs で `wedged=0`——**タグ側の Final 送信自体は
正常に予約・送信できていた**。つまり e30 の 0% は欠陥 2（送信予約の失敗）とは別の原因である。

原因は**受信窓の基準点の取り違え**だった。アンカーの `finalRxAfterResponseTxDelayUus` は
`dwt_setrxaftertxdelay()`（W4R: wait-for-response、送信完了後にチップが自動で受信を開始
する機能）に渡る値で、**自分（アンカー）の Response 送信完了時刻**を基準に数える。一方
タグの `finalTxDelayUus` は `dwt_setdelayedtrxtime()` に渡る値で、**Response の RMARKER
（フレームの基準時刻。タイムスタンプが打たれる瞬間で、同期ヘッダの終わりに立つ）**を基準に
数える。両者の基準点は Response 1 フレーム分の残り伝送時間（850 kbps・24 バイトで ≈267 µs、
下記で再導出）だけずれている。このずれはコードにも `docs/TIMING_PRESETS.md` にもこれまで
記載がなかった。

Response（24 バイト、850 kbps）の RMARKER 後の残り伝送時間: PHR（PHY Header、物理層
ヘッダ）≈21.3 µs + データ部 (8×24+48)×1.0256 µs ≈ 246.1 µs、合計 21.3+246.1 ≈ **267 µs**。

Response の RMARKER を基準点 R として（アンカー・タグの双方から見て同じ瞬間、伝搬遅延は
無視できるほど小さい）:

| | 1800/500（旧プリセット） | 1800/1500（e30） | 3000/1500（新プリセット） |
|---|---:|---:|---:|
| アンカーの受信窓が開く（R 基準） | R+780 µs | R+1806 µs | R+1806 µs |
| Final のプリアンブル先頭到達（R 基準） | R+1577 µs | R+1577 µs | R+2808 µs |
| 差（窓が開く − プリアンブル到達） | −797 µs（797 µs 早く開く） | **+228 µs（228 µs 遅れて開く）** | −1002 µs（≈1.0 ms 早く開く） |
| 結果 | 問題なし | **窓が開いた時点で残る SHR はわずか 41 µs → 毎回取りこぼす**（`rx_status` は RXPRD すら立たず RXFTO 単独） | 問題なし |

（「アンカーの受信窓が開く」は自分の Response 送信完了時刻 = R+267 µs を基準に
`finalRxAfterResponseTxDelayUus` を足した値。「Final のプリアンブル先頭到達」は
`finalTxDelayUus`（実 µs 換算）から SHR 269 µs を引いた値。）

**今回書いた Kconfig ヘルプの誤り**: 本日追加した `UWB_TWR_DIAG_FINAL_TX_DELAY_UUS`
（`firmware/twr/main/Kconfig.projbuild`）のヘルプ文には、当初「アンカー側の受信窓は自分の
Response 送信から `finalRxAfterResponseTxDelayUus`（1500）後に開くので、上書き値が 1500
以上であれば窓の内側に収まり受信される」という記述を書いていたが、**これは誤りである**
（両者の基準点が異なることをそのときは見落としていた）。e30 が実測でこれを反証した——
1800 は 1500 より大きいが、実際には一度も受信されない（0%）。正しくは上表のとおりで、
タグ側の値は Response **RMARKER** 基準、アンカー側の値は自分の Response **送信完了**基準
であり、両者は Response 1 フレーム分（≈267 µs、850 kbps/24 バイト）だけずれる。この誤りは
下の「今回追加した Kconfig」の項の直後で訂正した。

#### まとめ

前セッション（証拠 1・証拠 2、机上レビュー時点）が観測した 0〜23% は、**位相ロック
（欠陥 1、揃うと 0%）+ Final の予約締切失敗（欠陥 2、12.5%）**の組み合わせで説明がつく。
修正後は 88〜92%（再試行なし、e25/e26/e28/e29/e36）で、4 電文（Poll、Response、Final、
Result = "DWD"）それぞれが 1.5〜5% 落ちる積になっている。段の内訳はサイクルごとに揺れて
おり（e25 では response_wait ≈21 件・final_wait 12〜13 件・result_wait の RX_ERROR 32 件、
e26 では response_wait ≈30 件・result_wait 16 件）、**特定の電文が系統的に悪いとは言えない**。

#### 再試行系列（`UWB_TWR_RETRY_MAX=2`、即時再試行、e31〜e34）

| # | 構成 | 素の試行成功率 p | 周期成功率 | 1 回目失敗→2 回目も失敗 | 3 回目も失敗 |
|---|---|---:|---:|---:|---:|
| e34 | SS 850 kbps | 93.8%（694/740） | **99.9%（689/690）** | 3/40 = 7.5% | 1/3 |
| e31 | DS 850 kbps | 84.0%（669/796） | **96.5%（666/690）** | 31/71 = **44%** | 24/31 = 77% |
| e32 | SS 6.8 Mbps | 68.2%（668/980） | **96.2%（664/690）** | 68/217 = 31% | 26/68 = 38% |
| e33 | DS 6.8 Mbps | 29.6%（422/1426） | 61.2%（422/690） | 322/410 = 79% | 268/322 = 83% |

再失敗率の算出方法: 1 回目失敗数 = rescued（1 回目は失敗したが 2 回目以降で救われた
サイクル数）+ 周期失敗数、2 回目の試行数 = 1 回目失敗数、3 回目の試行数 = retries
（ログに記録された総再試行回数）− 1 回目失敗数。`CSEQ64`（サイクルごとの成否を 64 ビット
の列で記録するログ。前掲「証拠 1」参照）はサイクル単位の記録に過ぎず試行間の連続性
（1 回目が失敗したサイクルのうちどれが 2 回目も失敗したか）には使えないため、この間接的な
算出方法をとっている。

**SS-TWR は失敗が独立**（再失敗率がほぼ素の失敗率 1−p と同水準）で、再試行がそのまま
効く。6.8 Mbps の p は本日 0.68（前回 e12 は 0.80、アンカー温度 50〜54 ℃）。

**DS-TWR は 2 回目の失敗率が 1 回目の約 4 倍**（e31: 10.3% → 43.7%）。仮説: Response を
取りこぼしたタグは短時間で再試行するが、アンカーはまだ自身の Final 待ち窓（W4R 1500 UUS
+ RX タイムアウト 3000 UUS ≈ 4.9 ms、さらにホスト待ち 20 ms）の中にいて Poll を聞いて
いない可能性がある（詳細な機構は次項「再試行の待ち時間」で確認した）。e31 のタグ側失敗は
response_wait が 127 件中 ≈80 件で、再試行なし（e25: ≈21 件）の 4 倍。

DS 6.8 Mbps の p=0.30 は、SS 6.8 Mbps の 2 乗（0.682² ≈ 0.46）より悪い——DS-TWR の失敗は
SS-TWR の単純な 2 乗よりも系統的に重なりやすいことを示している。

#### 再試行の待ち時間（e37〜e41）

前項の仮説（アンカーが Final 待ち窓の中にいて即時再試行の Poll を聞いていない）を、
再試行前に待ち時間を挟んで実機で確認した。DS 850 kbps、`RETRY_MAX=2`、アンカーは
`anc_ds_dbg` 固定。

| # | タグビルド | 再試行前の待ち | 失敗ログ | 素の p | 周期成功率 | 1 回目失敗→2 回目も失敗 | 3 回目も失敗 |
|---|---|---:|---|---:|---:|---:|---:|
| e31 | `tag_ds850_r2` | 0（固定 2 ms 間隔のみ） | なし | 84.0% | 96.5% | 31/71 = 44% | 24/31 = 77% |
| e40 | 同上（再測） | 0 | なし | 80.2% | 96.1% | 38/97 = 39% | 27/38 = 71% |
| e37 | `tag_ds850_r2_lf` | 0 | **あり**（失敗ごとに `ESP_LOGW` 1 行） | 86.8% | 99.6% | 14/87 = 16% | 3/14 = 21% |
| e38 | `tag_ds850_r2_d10` | **10 ms** | あり | 88.5% | **100.0%（690/690）** | 6/84 = 7% | 0/6 |
| e39 | `tag_ds850_r2_d20` | 20 ms | あり | 88.6% | 99.7% | 14/73 = 19% | 2/14 = 14% |
| e41 | `tag_ds850_r2_d10nl` | **10 ms** | なし | 87.8% | **99.9%（689/690）** | 10/84 = 12% | 1/10 = 10% |

e40 は e31 と同じ構成の再測で、2 回目の失敗率は 39〜44% の範囲で再現した。10 ms 待つ
（e41）と 12% まで下がり、周期成功率は 96% 台から 99.9% に上がった。

**e37（待ちは 0 だがログあり）が 16% と大きく改善しているのは、失敗ごとの `ESP_LOGW`
（USB シリアルへ約 200 バイトを書き出す。所要 1〜2 ms）が明示的な待ちを入れていないのに
暗黙の待ちとして働いたため**である。10 ms（e38）と 20 ms（e39）の差は誤差の範囲
（2 回目の試行数が 70〜90 件しかない）。

**機構（机上の見積り）**: アンカーは自分の Response 送信完了後、W4R 1500 UUS + RX タイム
アウト 3000 UUS ≈ 4.9 ms の Final 待ち窓の中にいる（Poll 受信から数えると ≈8.2 ms まで）。
タグの response_wait 失敗は Poll 送信から 4〜6 ms 後に確定し、既存の固定 2 ms 間隔を足すと
再試行の Poll は Poll から 6〜8 ms 後に出る——**この時刻はまだアンカーの Final 待ち窓の
中であり、アンカーは Poll を聞いていないので再試行の Poll は失われる**（アンカー側は
`final_wait error=RX_ERROR` として記録する）。10 ms 待てば必ず窓の外に出る。

**推奨**: DS-TWR では再試行前に **10 ms 以上**（アンカーの Final 待ち窓 + 余裕）待つ。
Kconfig `UWB_TWR_RETRY_DELAY_MS=10` で周期成功率は 99.9%（e41）〜100.0%（e38）まで上がる。
SS-TWR では Response 待ち失敗の時点でアンカーはすでに Poll 待ちに戻っているため、この
待ちは不要（e34: 2 回目失敗率 7.5%）。5 台一巡の所要時間への影響は、再試行が起きる
サイクル自体が 12% 程度しかないため、平均で +1.2 ms/アンカー、最悪でも +20 ms 程度に
留まる。

再試行の待ち時間についての「次にやること」:
1. **本番機の PHY/プロファイルを決める**: 850 kbps + ポーリング（twr と同じ構成）を本番
   tag/anchor に Kconfig で選べるようにするか、BothIrq の DS プリセットを 6.8 Mbps で
   再導出・検証する。本番の既定のままでは卓上 p=5%（DS）——詳細は下の「本番タグへの
   再試行の実装と卓上確認（e42, e43）」参照。
2. ~~再試行（DS は ≥10 ms の待ちつき）を本番タグのスケジューラ（`firmware/tag`）に実装する。~~
   **実装・卓上確認済み（2026-08-30、e42, e43。下記「本番タグへの再試行の実装と卓上確認」
   参照）。** 再試行の機構自体は設計どおり動作したが、本番の既定 PHY/プロファイルの素の
   成功率が低すぎて実用にならないことが分かった（上記 1 が先）。
3. モジュールをホスト基板に重ねた状態と離した状態での 6.8 Mbps 比較はまだ実施していない。
4. StampFly 実機に載せた状態での p（素の試行成功率）の測定はまだ実施していない。
5. 割り込み駆動プリセット向けにさらに詰めた DS 設定が要るなら、Final 折返し時間の
   二峰性（通常 ≈0.7 ms / 遅い側 ≈1.6 ms、原因未確認）を先に調べる。

### データ速度と再試行の方針（2026-08-30、ユーザーと議論して合意した判断基準）

**背景**: SS-TWR の 99.95% は「850 kbps への変更 + 即時再試行 2 回」で得た。850 kbps は電文が 6.8 Mbps の
約 3 倍長く、DS-TWR で 5 台を一巡する時間はポーリングで 40〜50 ms（20〜25 Hz）、割り込み駆動で
プリセットを再導出しても 12〜16 ms（60〜80 Hz）。一方、**接点良好の卓上では 6.8 Mbps でも 80% 出ており**
（e12: 79.6%、1 m・平行配置）、そこに同じ再試行を足せば周期成功率は 2 回で 99.2%、4 回で 99.97% になる
（失敗が独立なら）。1 交換の所要時間は 6.8 Mbps ≈ 1.5 ms、850 kbps ≈ 3.2 ms（割り込み駆動）なので、
再試行込みの平均所要時間は 1.5/0.8 ≈ 1.9 ms 対 3.2/0.95 ≈ 3.4 ms で **6.8 Mbps + 再試行の方が約 1.8 倍速い**
（5 台一巡 平均 10 ms ≈ 100 Hz、最悪 40 ms）。「6.8 Mbps + 再試行」の周期成功率は**まだ実測が無い**。

【2026-08-30 実測】卓上・接点良好・`RETRY_MAX=2`・即時再試行で実測した（e32/e33、上の
「実機で確定した結果」節「再試行系列」参照）: **SS 6.8 Mbps は p=0.68・周期成功率 96.2%**、
**DS 6.8 Mbps は p=0.30・周期成功率 61.2%**。DS 6.8 Mbps はこの卓上条件でも判断基準表の
「p<0.6」帯に入っており、6.8 Mbps + 再試行だけでは足りない。

**注意（再試行が効かない条件）**:
- 6.8 Mbps は配置に弱い（向き試験で 4〜30%）。p=0.3 では 2 回再試行でも 66%。850 kbps の価値は
  「95%」ではなく悪い配置・飛行環境に対する余裕にある。
- 850 kbps では失敗直後の再失敗率が 10〜20%（独立なら 5%）と弱い連続性があった。6.8 Mbps の失敗は
  波形の崩れ（配置で決まる静的要因）なので静止した悪配置では連続しやすい可能性がある。飛行中は
  チャネルが数 ms で変わるので逆に再試行が効く側に転ぶかもしれない。要実測。
- 速度の自動切替（普段 6.8 Mbps、失敗が続けば 850 kbps）は、受信機が一度に一つの速度でしか待てず
  全アンカーの同時切替が要るので採らない。速度は運用ごとに一つ決める。

**判断基準（StampFly に実装した状態での試行成功率 p で決める）**:

   いない**が、これは DW3000 系チップでは普通の状態であり、OTP 経路でも
   SW（ソフトウェアのハードコード表）経路でも最終的にレジスタへ入る値は同じに
   なる。**DGC の設定ミスで受信感度の 30 dB 不足を説明することはできない。**
2. **kick ビットについて。** `OTP_CFG` レジスタの kick ビット（LDO 用 0x200 /
   バイアス用 0x400 / DGC 用 0x100）は「1 を書くと OTP の内容をレジスタへ転送し、
   転送完了後に自動で 0 に戻る」自己クリア型である。今回 `OTP_CFG=0x0000` と
   読めたのは自己クリア後にたまたま読んだだけであり、「kick していない」証拠には
   ならない。実際 LDO/バイアスの OTP 語が非ゼロなので、init 処理は必ず
   LDO/BIAS kick（`LDO_BIAS_KICK_E0` = 0x600）を書いている
   （`dw3720_device.c:959-963`）。旧版の L11 検査はこの `OTP_CFG=0x0000` を
   WARN（警告ログ）扱いにしていたが誤報だったため、INFO（参考情報）に直した。
3. **新説 (d) 水晶発振子が無調整でクロック偏差がある → 棄却。** L11 が読んだ
   水晶トリム OTP 語（アドレス 0x1E）は 2 台とも 0 で、SDK は 0 のとき既定値
   `DEFAULT_XTAL_TRIM`=0x2E（46）を代入する（`dw3720_device.c:1015-1020`、

出た変化はそれぞれ ≈0 dB と ≈−6 dB でしかなかった。

**分析（事実と解釈を区別して書く）**

1. **［確認済み・式で再現できた］RSL 推定式がそのまま成り立っている。**
   `rsl = 10·log₁₀(C·2¹⁷/N²) + 6·D − 121.7`［dBm］
   （`components/qm33120w_sdk/deca_rsl.c:36,81-105`。C=`ipatov_power`＝
   Ipatov 系列〔UWB のプリアンブルに使われる、自己相関特性に優れた符号
   系列〕の相関器が出す生の受信パワー、N=`accum`=109、D は DGC〔L11 で
   既出のデジタル利得制御〕が選ぶ 0〜7 の利得段、121.7 は PRF
   〔Pulse Repetition Frequency: パルス繰り返し周波数〕64 MHz 用の較正
   定数、2¹⁷ は `RSL_QUANTIZATION_FACTOR`〔`dw3720_device.c:161`〕）。
   C≈1000, N=109 を入れると D=0→−81.3 dBm、D=1→−75.3 dBm、D=3→
   −63.3 dBm となり、表1の 6 行すべてで「逆算した D」が整数（0〜3）に
   きれいに収まる。**受信機の DGC が C を毎回ほぼ一定（≈800〜1100）に
   正規化していて、`rsl_dbm` は実質 D の 6 dB 刻みでしか動いていない。**
2. **［解釈・注意］−81 dBm の頭打ちは熱雑音の底であり、それ自体は異常
   ではない。** 500 MHz の受信帯域の熱雑音電力は kTB（k=ボルツマン
   定数、T=絶対温度、B=帯域幅）から −174 dBm/Hz + 10·log₁₀(500×10⁶) =
   −174+87 = −87 dBm、受信機の雑音指数（NF: Noise Figure、受信機自身が
   加える雑音の目安）を ≈6 dB とすると −81 dBm になる。2.13 m 以遠では
   受信機は最大利得（D=0）に張り付いており、C は雑音に支配された値に
   なっている。**つまり距離を伸ばしても `rsl_dbm` が −81 dBm より下がら
   ないことは、それ単独では「雑音の底が高い」ことの証拠にはならない**
   ——この計器（rsl）では判定できないというだけである。候補 (a)（広帯域
   の妨害波／雑音の底が高い）は、この頭打ちを根拠に扱わないこと。判定は
   「未確認・この計器では判定不能」のまま据え置く。
3. **［確認済み］成功率は受信電力にほぼ依存しない。** 0.3 m→3.4 m
   （受信電力にして ≈−64→−81 dBm、17 dB の差）でも、送信電力レジスタを
   0xfe→0x00 にしても、成功率は 9〜20% の帯から外に出なかった。むしろ
   同一配置・同一設定を 2 回繰り返した 0.3 m の 2 run（16.2% と 9.7%）の
   方が差が大きい。**0.3〜3.4 m の範囲でこのリンクは SNR（信号対雑音比）
   律速ではない**——失敗は受信電力とは別の原因で、フレームごとに独立に
   起きている。
4. **［確認済み］失敗は時間的に独立していて、バースト状の妨害ではない。**
   10 回区切りごとの成功数の分散は、2 項分布から期待される理論分散との
   比が 6 run 全部で 0.74〜1.15 に収まっており、数百 ms 以上続く周期的な
   妨害は否定される。RXFTO（タグ側が応答を待ってタイムアウトした行。
   アンカー側がポールフレームの復号自体に失敗して応答を返さなかった
   場合もタグ側からは RXFTO に見える）を踏まえると、往復 2 フレーム
   （ポール／レスポンス）のどちらかで RXFSL（Reed-Solomon 復号失敗）が
   起きていると読める。成功率 15%≈0.39² から逆算すると、**1 フレーム
   あたりの成功率は約 39%、つまり毎回およそ 6 割が落ちている計算になる。**
5. **［事実＋解釈］送信電力レジスタが出力にほとんど効いていない。**
   レジスタの読み戻しは要求値と一致しており（書き込み漏れではない）、
   SDK 自身の利得表で積算すると 0xfe→0x3e で ≈10.8 dB、0xfe→0x00 で
   ≈30 dB 下がるはずなのに、受信側で観測できた変化はそれぞれ ≈0 dB と
   ≈−6 dB だった。**最有力の解釈: 送信チェーンが飽和・非線形になって
   いて、レジスタ設定によらずほぼ一定の（歪んだ）出力を出している。**
   これは、6.8 Mbps での RS 復号失敗が受信電力によらず起きていること、
   および 850 kbps（1 シンボルあたりの積分時間が長く、歪んだパルスにも
   強い）で成功率が上がる（上部「核心の数字」参照）ことと整合する。
   **ただしこの計器（ソフトウェア経由の間接推定）だけでは、受信機側の
   DGC／電力推定が高入力側で圧縮されている可能性を排除できない。**
   2 台は同一ロットで挙動が一致しているため、個体差ではなくロット単位の
   モジュール特性という見方もできる。いずれも外部計測器なしでは確定
   しない。
6. **［事実・手順上の注意］配置・run 間のばらつきが大きい。** 同一配置
   （0.3 m）を 2 回連続で測っただけでも成功率は 16.2%→9.7%（差 6.5 pt）
   動いた。**今後の A/B 比較は 1 条件 1 run では判定しないこと。** 最低
   2 run を取るか、効果がこのばらつきより明らかに大きい場合に限って
   結論を出すこと。

**新設した計器:** Kconfig `UWB_TWR_DIAG_TXPOWER`（16 進数、既定
0xfefefefe。`firmware/twr/main/Kconfig.projbuild`）で `TX_POWER`
レジスタを上書きできるようにし、起動ログの `phy: ...` 行に
`txpower=0x%08lX pgdelay=0x%02X` を追記、`begin()` 直後にレジスタを
読み戻す `tx_power readback=0x%08lX (requested 0x%08lX)` 行を追加した
（`firmware/twr/main/main.cpp`）。本ドキュメントと同じコミットで
取り込み予定。

配置を、机上・段ボール箱の上という置き方から、樹脂棒（プラスチック製の棒）
2 本の上に基板を渡してアンテナ高 104 cm に固定する置き方へ変え、周囲

6.8 Mbps / SS-TWR / PollingBoth）。**置き方を変えただけでは何も変わらな
かった**（机上・段ボール箱をやめた直後、変更前と同じ 0.7 m 相当の配置でも

**較正レジスタダンプの比較**（`firmware/twr` に新設した起動時の `cal:`

| 項目 | 冷起動 29.2 ℃（良: 37.7%） | 温起動 36.5〜37.6 ℃（悪: 7.8〜12.5%）×3 |

ADC しきい値較正は冷起動・温起動で完全一致しているので、**違いを生んで
いるのは PLL の粗調整コード（VCO の粗調整コード）と PGF 較正結果の
1 ビットだけである。** ADC 較正（前節「残っている候補」(b) の一部として
検討していたもの）は今回も差の説明にならない。

**ランタイムでの再較正を試したが、どれも直らなかった。** `firmware/twr`
に足した Kconfig `UWB_TWR_DIAG_RECAL_KIND`（ADC / PGF / PLL / FULL）と
`UWB_TWR_DIAG_RECAL_SEC`（起動から何秒後にやり直すか）で: 温起動した
タグに対して起動 40 秒後に ADC オフセット較正だけをやり直すと
11.7%→10.5%（レジスタ値も変化なし）。32.3 ℃ 起動のタグに対して起動
300 秒後に PLL 再較正（`dwt_pll_cal()`）をやり直すと、コードは 0x24 の
まま、16.4%→18%。SDK の関数
`dwt_pll_chx_auto_cal(DWT_CH9, 0x23, 500, 1, 0)`（Kconfig
`UWB_TWR_DIAG_PLL_COARSE_CH9`）で粗調整コードを直接 0x23 へ強制しよう
としたところ、**戻り値 254（`uint8_t` としては `DWT_ERR_PLL_LOCK`=−2 の
2 の補数表現＝ PLL ロック失敗）・読み戻しは 0x24 のまま・成功率 7.8% と
失敗した。** この関数（`ull_pll_ch9_auto_cal`、
`components/qm33120w_sdk/dw3720/dw3720_device.c:8218`）は init が実際に
使っている経路ではない。init は `ull_setdwstate(DWT_DW_IDLE)` 経由の
ハードウェア較正（`PLL_CAL` レジスタの `PLL_CAL_EN` ビットを立てて自動
探索させる方式、同ファイル 1097〜1130 行 / 8061〜8087 行）を使っており、
`dwt_pll_chx_auto_cal()` はコード自体は ch9 用に渡せても `PLL_CFG`
レジスタを **ch5 用の設定で** 上書きしてしまう（同ファイル 8253 行の
コメントに「これは CH5 の設定」と明記されている）ため、狙ったコードへ
固定する用途にはそのままでは適さない。**未試験:** 生レジスタを直接
叩く経路（`PLL_COARSE_CODE` の ch9 フィールドへ書き込み、`PLL_CAL` の
`PLL_USE_OLD`（ビット1、0x2）と `PLL_TUNE_OVR`（ビット2、0x4）を立てて

**解釈（まだ確定していない読み筋）。** 起動時のダイ温度が高いと（この
個体ではおよそ 31 ℃台と 32 ℃台の間が境目）、ハードウェアの PLL 較正が
VCO 粗調整コードとして工場値 0x23 ではなく 0x24 を選ぶ。PLL 自体はロック
する（ロックフラグは 1 のまま）ので初期化は正常に完了して見えるが、
工場値より位相雑音やチューニング余裕が悪いコードに乗っている可能性が
あり、それが 6.8 Mbps のペイロード復号失敗（受信電力に依存しない、
フレームごとに独立、その起動が続く限り一定）として現れている、という
筋である。これは §0-B のこれまでの全観測——受信電力に依存しないこと、
送信電力を絞っても変わらないこと、850 kbps にすると改善すること、
「配置に敏感」と見えていたものの正体が実は起動ごとのばらつきだった
こと——と矛盾しない。また `docs/archive/REIMPL_PLAN.md` の【R10】

不要）と根は同じ現象と考えられるが、**今回見えているのは「運転中の
温度ドリフト」ではなく「起動という一点で較正がどちらのコードを選ぶか」
であり**、この節冒頭の表・および前節冒頭6.（アンカーのダイ温度が運転中に
39.7→52.3 ℃ 上がっても瞬時成功率に下降傾向が出ない）を否定するもの
ではない——あちらは同一起動内でのドリフトを見ており、こちらは起動の
瞬間に固定される初期値の話である。この個体の境目が室温に近いため、
これまで「起動のたびに結果が違う」ことが配置や日によるランダムな揺らぎ
に見えていた、と説明がつく。

**追記（同日夜、生レジスタ固定の実機結果）。** `UWB_TWR_DIAG_PLL_COARSE_CH9` を
`dwt_pll_chx_auto_cal()` 方式から生レジスタ方式へ書き換えた（`PLL_COARSE_CODE` の
ch9 フィールドへ書き込み → `PLL_CAL` の `PLL_USE_OLD`（0x2）と `PLL_TUNE_OVR`（0x4）を
立てる → `dwt_setdwstate(IDLE_RC)` → `dwt_setdwstate(IDLE)` で再ロック。A: USE_OLD のみ /
B: USE_OLD+TUNE_OVR / C: 較正なしで再ロック、の順に自動で試す）。**A ではハード較正に
上書きされて 0x24 に戻るが、B で 0x23 に固定され PLL はロック維持（`pll_status=0x63`、
`pll_cal=0x87`）。温起動 37.6 ℃のタグで 0x23 を固定した結果 36.8%（254/690）**——固定前の
温起動 7.8〜12.5% から冷起動並みへ回復した。これで候補 (e) は「最有力」から
**「実機で因果を確認済み」**へ格上げする。

アンカー側（連続受信で 56.5 ℃、ハード較正は **0x25** を選ぶ）でコードを振った結果
（タグは 0x23 固定のまま、各 95 秒 = 690 回の同一区間比較）:

| アンカーのコード | タグ側の成功率 |
|---|---|
| 0x22（強制） | 6.8% |
| 0x23（強制、3 回） | 21.7% / 26.4% / 26.7% |
| 0x24（強制） | 17.0%（別区間・39.7 ℃起動時のハード較正値 0x24 では 36.8%） |
| 0x25（57 ℃でのハード較正値） | 7.5% |

読み: 最適コードは温度で動き（≤31 ℃: 0x23、57 ℃: 0x23〜0x24）、**ハード較正は
温かいとき最適より 1 段高い値を選ぶ**（37 ℃で 0x24、57 ℃で 0x25）。両端のコードは
はっきり悪い。同一条件でも ±5〜10 pt ぶれるので、細かい順位付けには n≥2 が要る。
なお、このセッションで観測した最高値 64.8% は「タグ冷起動 0x23 ＋ アンカー 0x24
（39.7 ℃起動のハード較正値）」の組合せだった。

#### ネット調査（2026-08-29 夜）: 「このチップは本来どれだけ出るか」

ユーザーの指摘「良い状態でも 40〜65% を正常と見なす根拠が乏しい」を受けて調査した。
結論: **近距離 LOS では 99% 以上が本来の姿で、65% は異常。** 根拠:

- DW3000 データシートの受信感度は **PER（パケット誤り率）1%** で規定されている
  （ch9 6.8 Mbps ≈ −93 dBm、850 kbps ≈ −99 dBm。PDF 本文の直接引用は取れず検索結果の
  転記なので要確認）。Mouser の製品概要も「感度点から 3 dB 戻した点で PER 1%」と記す。
  https://www.mouser.com/pdfDocs/DW3000DataSheet5.pdf
- 学術論文（Han & Jang, Sensors 25(10):3058, 2025）は 802.15.4z HRP UWB の到達距離評価で
  PER 1% を「失敗」の基準に置き、屋内 90 m 超・屋外 300 m 超まで 90% 以上の成功率を報告。
  1.5 m で 65% は劣化曲線の外。 https://www.mdpi.com/1424-8220/25/10/3058
- Qorvo フォーラムでは実機で 4921/5000 = 98.4% の受信成功が報告され、Qorvo 側は
  「99% の CRC 良好率が得られる減衰量で感度を測る」と答えている。
  https://forum.qorvo.com/t/reed-solomon-error/6781
- 高 SNR で RXFSL/RXPHE が多発するとき Qorvo スタッフが挙げる原因は
  (1) 送受信の PHY 設定不一致（本件は同一ファームなので除外）、
  (2) **RF ハードウェア**（IC 直下のグランド、RF 配線、アンテナ）。後者の診断で
  「Ipatov 相関器の電力が異常に低い（正常は 20000〜30000、異常例はほぼ 0）」を
  根拠にしている。 https://forum.qorvo.com/t/whats-possibly-wrong-with-this-diagnostic-information/13840
  **本件の `ipatov_power` は全条件で約 800〜1200 で、この「正常値」より 13〜15 dB 低い。**
  （同じ `dwt_readdiagnostics()` の `ipatovPower` を指しているかは要確認。）
- QM33120W は送信バースト時に 200〜250 mA の電流ピークを引く（web 情報。§0-B 末尾の
  「一次資料による再検討」で後述のとおりデータシートの実測値とは食い違う）。Qorvo のレイアウト指針は
  短い配線と近接デカップリングを求める。電源の瞬時電圧降下は PLL/VCO を乱しうる
  （本件は M5StampS3A の 3.3 V レギュレータ経由の USB 給電。未測定）。
- M5Stamp UWB（QM33120W）固有の成功率報告・不具合報告は英語・日本語とも見つからず
  （GitHub issue 0 件、発売直後）。「問題なし」の証拠ではなく、公開データが無いだけ。
- PLL 粗調整コードの温度ずれそのものは、Qorvo の API ガイド（`dwt_settemperature()` /
  `dwt_pll_cal()` / `PLL_STATUS` の VCO_TUNE_UPDATE フラグ）が「PLL 較正は温度依存」を
  前提にしている以外、フォーラム・エラッタ・リリースノートに記載なし（未報告の症状）。
  https://forum.qorvo.com/uploads/short-url/xD3TlXKvkujjdUaJWXv2b4E7GQN.pdf
  受信側の PGF 較正は「起動時・ウェイク後・20 ℃の温度変化後に再実行」が通例とされる
  （非公式まとめ）。 https://gist.github.com/egnor/455d510e11c22deafdec14b09da5bf54

読み: PLL 粗調整コードは **起動ごとの 10〜25% ↔ 40〜65% の振れ**を説明するが、
**99% との差（ベースの劣化）は別にある。** 残る本命は RF ハードウェア／電源
（2 台が同一ロットなので基板・モジュール側の共通要因）。

   ドライバのファイル名（`dw3720_device.c` 等）にだけ残っている。
2. **【事実＋解釈】自己ベスト 65% とデータシートの差は大きい。**
   データシートの受信感度は **PER（パケット誤り率）1%** で規定されており、
   ch9・6.8Mbps で **−91dBm**（§5 の表）。本件は推定 RSL（Received Signal
   Level: 受信電力の推定値）−64〜−81dBm という「良い」起動状態ですら
   35〜90% しか成立していない。**【解釈】** これは規定の感度点より
   約 25〜30dB 弱い電力条件で 65% 前後しか出ていないということであり、
   正常なチップの挙動としては説明が付かない差である。
3. **【事実＋解釈】電源ピーク電流説は後退させる。** データシートのピーク
   電流は、連続 RX の試験モードでも最大 107mA、1フレームぶん（47µF 付き）
   なら 17〜19mA にとどまる（§5 の表）。**【解釈】** web 上で見つけた
   「送信バーストで 200〜250mA」という主張は、データシートの実測条件とは
   一致しない。電源電圧の実測（オシロスコープでの3.3V観測）自体は
   まだ行っていないが、優先度は下げる。
4. **【解釈】ドライバのコード自体に欠陥がある可能性は下がった。**
   同梱ドライバは公式版と機能的に同一（§5）なので、ドライバのロジックに
   本件特有のバグがある可能性は低い。init 手順も Qorvo の公式サンプル
   （`ex_06a`）と同じ骨格（`dwt_configure()` の戻り値を確認、PGF
   （Programmable Gain Filter: 可変利得フィルタ）較正は `configure` の中で
   実行、PLL 較正は `configure` 時に一度だけ、ADC 較正も `configure` 時）
   で、手順の逸脱は見当たらない。
5. **【事実】PLL ステータスレジスタは良否を区別しない。**
   `dwt_readpllstatus()`（ビット定義: b0 CPC_CAL_DONE、b1 LOCK、
   b2 LO_FLAG_N、b3 HI_FLAG、b4 OVRFLOW、b5 VCO_TUNE_UPDATE、
   b6 XTAL_AMP_SETTLED、b8-12 LD_CODE）は、冷起動・良好（0x63）、
   温起動・不良（0x63）、57℃起動のアンカー（0x63）のいずれも**同じ 0x63**
   （CAL_DONE + LOCK + VCO_TUNE_UPDATE + XTAL_AMP_SETTLED、HI_FLAG/OVRFLOW
   はクリア）だった。実行時の再較正だけが 0x67（LO_FLAG_N が立つ）を出した。
   **つまりステータスフラグからは、良い/悪いの粗調整コードの違いは見えない。**
6. **【解釈】残る「ベースの劣化」の候補（起動時の粗調整コード効果とは別）。**
   一次資料が新たに示した候補:
   - (a) **基板ごとの送信校正が前提とされている。** Qorvo は送信電力・
     PG delay（送信パルス発生器の遅延で、送信パルスの帯域幅を決める設定値）・
     PG count（送信帯域の温度補正に使う、工場で室温実測が必要な値）は
     いずれも評価ボード向けの値だとしており、M5Stamp UWB モジュールには
     基板単位の OTP 較正が入っていない（水晶トリムの OTP 語は 0、
     TX_POWER レジスタを変えても本日の実測では受信電力はほぼ変わらな
     かった）。→ 次の一手は PG delay の掃引と送信スペクトルの外部計測。
   - (b) **モジュールの RF ハードウェア。** Qorvo フォーラムでは、Ipatov
     相関器（受信波形の到来時刻・電力を推定する相関処理の一種）の電力が
     低いケースを、担当者がグランド・RF 配線・アンテナの問題として診断
     している例がある。本件の `ipatov_power` は約1000でほぼ一定だが、
     これが「低い」と言えるかは比較対象の基準値が要る（未確認）。
   - (c) **SDK 自身のサンプルは既定で ch5 を使う。** 本モジュールは ch9
     専用（ユーザー確認済み）なので、SDK のサンプルをそのまま踏襲した
     比較はできない。

#### 電源経路の調査（2026-08-29 夜、ユーザー依頼）

ユーザーの質問「StampS3 の DC-DC（MUN3CAD01-SC）は UWB 駆動条件に合っているか」に対する調査結果。

- **部品の同定: 実基板は MUN3CAD01-SC で確定**（2026-08-29 ユーザー目視: レギュレータ脇に
  独立したコイルが無い＝コイル内蔵の uPOL モジュール）。回路図 `Sch_StampS3_v0.3.3.pdf` の
  JW5712 は別版（旧版）の設計であり、手元の M5StampS3A とは一致しない。以下の経緯は記録として残す。
- **（経緯）部品の同定に食い違いあり。** M5Stack の StampS3 製品ページは DC-DC を
  MUN3CAD01-SC（**Cyntec**〈Delta グループ〉の uPOL モジュール。Murata ではない）と記載。
  一方、手元の `assets/Sch_StampS3_v0.3.3.pdf` の U4 は **JW5712**（外付けコイル L4 = 2.2 µH、
  印字「IOUT: 0〜0.6A」、出力 10 µF × 3）。基板改版で置き換わった可能性。実基板で
  「レギュレータ脇に独立したコイルがあるか（JW5712 系）／2.9×2.3 mm 6 端子ブロックのみか
  （MUN3CAD01-SC、コイル内蔵）」を目視で確認すること。
- **MUN3CAD01-SC の仕様**（Cyntec データシート Rev.07）: 入力 2.7〜5.5 V、出力 0.8〜4.0 V
  （外付け抵抗で設定）、**1 A 連続**、3 MHz PWM、軽負荷では省電力（パルススキップ）モードへ
  自動移行、リップル 15〜20 mVp-p typ、**50→100% 負荷ステップで ±30 mV**、Cout(max) 150 µF、
  外付け出力コンデンサ「推奨」、過電流 1.3〜2.5 A（非ラッチ）、EMI/スペクトラム拡散の記載なし。
  https://m5stack.oss-cn-shenzhen.aliyuncs.com/resource/docs/datasheet/Stamp/S007%20StampS3/MUN3CAD01-SC.pdf
- **QM33120W 側の要件**（データシート Rev. D p.10-11）: VDD1 1.62〜3.6 V、VDD2a/b **2.4〜3.6 V**、
  VDD3 1.5〜3.6 V（モジュールは VDD3 を自前の 1.8 V DC-DC〈JW5712〉で給電）、POR しきい値
  VDD2 ≈ 2.2 V / VDD3 ≈ 1.4 V。電流は連続 RX ch9 61/82/107 mA、TX ch9 最大 76 mA、単一フレーム
  平均 17〜19 mA（**「47 µF コンデンサ付き」の測定条件**）。リップルの数値要件は無く
  「余裕を考慮せよ」のみ。推奨回路は VDD 直近に 10 µF、VDD2a はフェライトビーズ経由。
- **回路図から確認した事実**: (1) モジュール側の 3.3 V には 100 nF / 4.7 nF しかなく、
  推奨の 10 µF も試験条件の 47 µF も無い（10 µF はすべて 1.8 V DC-DC の周辺）。
  (2) StampS3 の 3V3（FPC 11 番）はレギュレータ出力に直結（ビーズ・ヒューズなし）で、
  FPC＋ジャンパ線を経由。(3) RF1 経路にフィルタなし、RF2 は 49.9 Ω 終端。
  (4) 水晶負荷容量 3.3 pF は推奨回路と一致。
- **判定**: 電圧・電流・応答とも静的には十分（負荷は ESP32-S3 数十〜100 mA ＋ UWB アイドル
  29 mA ＋ バースト時 +80 mA 程度）。「条件に合っていない」とは言えないが、**モジュール直近の
  バルク容量が推奨より 2 桁少なく、Qorvo が性能を規定した条件（47 µF）から外れている**。
  受信バースト立ち上がり（≈100 mA を µs 級）で配線インダクタンスにより瞬間的な電圧降下が
  起きる経路になっている。ネット調査で出た「200〜250 mA のピーク」は本チップには非該当。
- **提案**: モジュールの VCC_3V3–GND 直近に 47〜100 µF の低 ESR コンデンサ（＋10 µF セラミック）
  を足し、同一ファーム・同一状態（粗調整コード固定）で成功率を比較する。可能なら測距中の
  3.3 V をモジュール端で AC 結合・20 MHz 帯域で観測。`docs/WIRING.md` の「12 mVpp」は根拠不明
  として撤回済み。

清掃・確実な固定**（または短い直付け配線）を最初に行い、その状態を基準にやり直す。

#### 【到達】タグの即時再試行でサイクル成功率 99.95%（2026-08-29 午後）

850 kbps では素の試行成功率が 93.5〜97% で頭打ちになり、PHY 側の残りの手（SFD・符号・PG delay・
応答遅延・割り込み駆動）はいずれも効かなかった。一方、失敗の並び（`SEQ64`）は孤立したものが大半だった
ので、**失敗した交換をその場でやり直す**（`UWB_TWR_RETRY_MAX`、コミット `e6dfca5`）:

| 試験 | サイクル数 | サイクル成功 | 試行ごとの成功率 | 再試行 / 救済 |
|---|---|---|---|---|
| `RETRY_MAX=2`、95 秒 | 690 | **690 / 690 = 100%** | 94.1%（696/740） | 44 / 35 |
| `RETRY_MAX=2`、300 秒 | 2,180 | **2,179 / 2,180 = 99.95%** | 95.1%（2188/2300） | 111 / 100 |

- 1 サイクル = 137 ms 周期の 1 回の測距機会。再試行は 2 ms 後に新しいシーケンス番号で Poll を打ち直す
  （1 交換 ≈ 5〜8 ms なので、上限 5 回でも周期内に収まる）。
- 失敗直後の再失敗率は ≈ 10〜20%（独立なら ≈ 5%）で、**失敗は弱く連続する**。それでも 3 回目まで
  全部落ちるのは 2,180 サイクルに 1 回。
- 距離: 中央値 1.033 m、min 0.93 / max 1.13 m（テープ実測 ≈ 1.0 m）。再試行で距離の質は変わらない。
- 6.8 Mbps のまま再試行しても 80% → 1 − 0.2³ ≈ 99% 止まりで、連続性を考えるとさらに下がる。
  **850 kbps への変更と再試行の組合せが要点。**

**推奨構成（この 2 個体・1 m・向き 1）**: 850 kbps / preamble 256 / PAC16 / SFD DW8 / 符号 9 / PG 0x34 /

### 配置への異常な敏感さ（実験手順として必ず守ること）

既定 PHY は配置に極端に敏感で、**置き場所を変えながらの A/B 比較は成立しない**。

| 配置 | 既定 PHY | robust PHY |
|---|---|---|
| 木のテーブル上（床から 72 cm、天板から 4 cm） | 38.9% → 別測定で 22.3% | 56.8% |
| 床から 28 cm（段ボール箱） | 5.0% | 64.1% |
| 机上・2 台とも USB ケーブルで Mac に接続したまま（距離未計測、上 2 行の 540 mm 配置とは別構成、2026-08-29） | **8.8%**（57/650、90 秒） | 未測定 |

robust PHY はほぼ位置に鈍感。**設定を比較するときは必ず配置を固定し、同一セッション内で
連続して測ること。** 日をまたぐ・置き直すと基準が動く。上の 3 行目も基準がどれだけ
動くかを追加で裏付けている（失敗の `rx_status` は引き続き RXFSL / RXPHE、
`rsl_dbm` ≈ −69 dBm で他の測定と同系統）。以後の A/B 比較で「既定 PHY は 22%」の
ような単一の数字を固定基準として使わないこと。

なお 2 波モデル（直接波と床面反射波、行路差 Δ ≒ 2h²/d、合成振幅 2·|sin(πΔ/λ)|、
λ = 3.75 cm）では、d = 0.54 m・h = 0.04 m のとき Δ = 5.9 mm で自由空間比 −0.5 dB となり、
テーブル上の配置は本来ほぼ損失がない。**「低すぎるから打ち消している」という説明は
実測で棄却された**（持ち上げたら悪化した）。

### 計器の読み方の注意（重要）

CIA 診断レジスタは SYS_STATUS をクリアしても消えない。したがって
**RXFTO（何も受信していない）の行に出る `rsl_dbm` / `fp_dbm` / `accum` は、
前に受信した良品フレームの残りである。** `accum` が毎回同じ値になるのはこのため。
必ず `rx_status` と併せて読み、RXFTO の行の電力値は捨てること。

## 0-A. 【棄却済み】SS/DS-TWR がほぼ成立しない件（2026-08-28 に立てた説）

> **この節の結論は 2026-08-29 の実機測定で棄却された。** 上の §0-B が正本。
> `tx_margin_us` は常に正（+615 µs / +2785 µs）で締切は一度も割っておらず、
> IRQ 線も 2 台とも生きている（probe L5 が PASS）。
> 以下は経緯の記録として残す。

### 結論（コードと一次資料だけで確定。実機では未検証）

**IRQ（割り込み）を前提にしたタイミングプリセットが、実際にはポーリングで動いている
ファームに適用されていた。** IRQ プリセットの折返し締切（約 900 µs）は、ポーリングの
折返し時間（約 1.2 ms）では構造的に守れない。

連鎖はこうなっている。

1. **Kconfig の既定は `UWB_TIMING_PROFILE_BOTH_IRQ`**
   （`firmware/twr/main/Kconfig.projbuild`、`firmware/anchor`・`firmware/tag` も同じ。
   ビルド済み `firmware/twr/sdkconfig` も `CONFIG_UWB_TIMING_PROFILE_BOTH_IRQ=y`）。
   **ソース中の多数のコメントが「既定は PollingBoth」と書いていたが、これは事実と違った**
   （2026-08-28 に訂正済み）。過去のコミットメッセージが実測条件を「PollingBoth」と
   記録しているものも、この誤ったコメントに引きずられた可能性がある。
   **どのプリセットで焼いたかは、いまや起動ログに出る（下記「観測できるようになったもの」）。**

2. `BothIrq` / `AnchorIrq` の `responseTxDelayUus` は **878 UUS ≒ 900 µs**。
   この値は [`TIMING_PRESETS.md`](TIMING_PRESETS.md) §1.3 が「IRQ 駆動の折返し ≒ 0.3 ms」を
   前提に置いた数字である。同じ §1.3 が**ポーリングの折返しを「気づくまで最大 1000 µs ＋
   SPI と計算 100〜200 µs ＝ 約 1.2 ms」と見積もっている。** 締切のほうが短い。

3. **`uwb_port_irq_enable()` の成功は「ISR を登録できた」ことしか意味しない。**
   DW_IRQ が `pin_irq` に本当に繋がっているか、極性が合っているかは一切見ていなかった。
   線が死んでいても `irqActive()` は true を返し、起動ログは `irq=active` と出る。
   一方 `uwb_port_irq_wait(1)` は毎回 1 ms のタイムアウト待ちに落ちる ＝ 実質ポーリング。
   **本リポジトリは IRQ 線の導通を一度も確認していない**（§1「取れていないのは
   RSTn(G6) / IRQ(G7) / WAKEUP(G8)」）。

4. 締切を割った遅延送信は、SDK が黙って遅れて送るのではなく**送信ごと取り消す**。
   `components/qm33120w_sdk/dw3720/dw3720_device.c` の `ull_starttx()`:
   HPDWARN（Half Period Delay Warning）を見て `CMD_TXRXOFF` を発行し `DWT_ERROR` を返す。

5. 結果、アンカーは Poll を**聞いているのに** Response を一切出さない。タグ側からは
   **「RXFTO のみ・RXPRD も RXSFDD も立たない」**＝電波が来ていないのと区別できない
   失敗に見える。2026-08-28 に実測した `rx_status=0x000200F4` はまさにこの形である。

### 観測データとの整合（この説明だけが全部と矛盾しない）

- **距離・向き・役割の入替え・ダイ温度・PHY の頑健化（preamble 1024 / 850 kbps）・
  外部 LNA/PA のどれを変えても成功率が動かなかった**のは、損失が電波側ではなく
  ホストのスケジューリング側にあるなら当然である。
- **数十秒周期の「うなり」**は、2 台の 1 ms tick（FreeRTOS のタイマ刻み）の相対ドリフトで
  説明できる。水晶の相対誤差 25 ppm なら位相が 1 ms ぶんずれるのに
  $1\times10^{-3} / 25\times10^{-6} = 40\ \mathrm{s}$。記録にある
  「起動後 4.000 秒は 20/20 成功、その後 40 秒ほぼ無反応」と桁も形も合う。
- 成功率 18.1% は、1 ms の tick 位相のうち締切に間に合う割合が 18% だったと読める
  （＝折返しの実測が約 900 − 180 = 720 µs 程度）。
- **逆に `PollingBoth`（締切 3077 µs）ではこの周期性は原理的に出ない。** 余裕が
  1 ms tick より大きいので、位相がどこにあっても間に合う。
  **うなりが観測されたこと自体が、焼かれていたのが IRQ プリセットだった状況証拠になる。**

### 棄却した説

- **「アンカーの受信窓と Poll 周期のうなり」（`12c5dbc` で立てた説）は成立しない。**
  `respondRange()` は `dwt_setrxtimeout(0)`（フレーム待ちタイムアウト無効）で受信機を開き、
  窓が満了するまで開けたままにする。呼び直しの合間に閉じている時間は SPI 数回ぶん（µs）
  しかないので、**受信デューティは窓長によらず 99% 以上**あり、1〜18% を説明できない。
  該当箇所のコメントは訂正済み。
- **SPI 16 MHz が化けている説**も、データシート上は無理がない
  （`assets/QM33120W Data Sheet.pdf` Rev.D p.25/p.26: 最大 32 MHz、
  `t2`（SCLK→出力）Max 9.5 ns、`t3`（セットアップ）Min 2.5 ns。16 MHz の半周期 31.25 ns に対し
  十分な余裕がある）。**優先度は下げてよい**（ただし実測で否定したわけではない）。

### 実機が来たら、この順で（反証の形で書いてある）

1. **【最優先・新ファーム不要】両機を `CONFIG_UWB_TIMING_PROFILE_POLLING_BOTH=y` で焼き、
   50 秒採る。**
   - 成功率が大きく上がれば（例: 50% 以上）→ 本説は支持される。
   - **変わらなければ本説は棄却。** その場合は下の 2・3 で別の切り分けに移ること。
2. **新ファームで起動ログの `irq self-test` を読む。**
   - `FAILED`（事象は起きたがエッジが来ない）→ IRQ 線が死んでいる。§0-A の前提どおり。
   - `OK` → 線は生きている。**その場合、本説の前提3が崩れる**ので、代わりに
     「IRQ が生きていても折返しが 900 µs に間に合っていない」を疑い、3 の `tx_margin_us` を見る。
   - `spurious edge` → 未配線でフロート、または極性が逆。
3. **アンカーの `tx_margin_us` を読む。これが今回の主計器。**
   - 負の値が出ていれば「Poll は聞こえていたが送信が取り消された」の**直接の証拠**。
     `error=TxStartFailed` の件数がタグの失敗数と同オーダーで並ぶはず。
   - 正で大きければ（例: `PollingBoth` で +1800 µs 前後）締切は原因ではない。**別を探すこと。**
   - `responseTxDelayUus` の実 µs 値からこの残りを引けば**折返しの実測値**が出る。
     [`TIMING_PRESETS.md`](TIMING_PRESETS.md) §1.3 の見積り（ポーリング約 1.2 ms /
     IRQ 約 0.3 ms）はこれで初めて検算できる。**実測が見積りより大きければ、
     プリセットの数値そのものを実測に合わせて引き直すこと。**
4. アンカーの失敗内訳（`error=` の分布）を見る。`TxStartFailed` ではなく
   `RxTimeout` ばかり（＝ログが出ない）なら、アンカーは Poll を**聞けていない**ので
   本説は棄却。受信側の切り分けへ戻る。

### まだ直していない・確認していないこと

- **`respondRange()` は回復可能な受信エラー（RXPHE / RXFCE / RXFSL / RXSTO / ARFE /
  CIAERR）1件で受信窓を放棄して return する。** Qorvo 公式の responder サンプル
  （`ex_06b_ss_twr_responder`）はエラーを消して `dwt_rxenable()` し、待ち続ける。
  今回は「アンカーの失敗計数の意味を変えると前後比較が読めなくなる」ため**あえて触っていない**。
  §0-A の主因が片付いたあとに直すこと。
- **`hostTimeoutMs = 10 ms`** は、チップ側 RX タイムアウト（`PollingBoth` で 4615 µs）1回ぶん
  しか吸収できない。不一致フレームを1枚拾って `dwt_rxenable()` で再アームされると
  10 ms を超え、`RxTimeout` が `rxStatus = 0` のまま返る（＝せっかくの診断が消える）。
  M5Stack 公式サンプルは 100 ms。**今回は A/B 比較を濁さないため据え置いた。**
- **アンカーの電源。** データシート p.11 Table 5 の連続受信ピーク電流は
  **ch9 で typ 82 mA / max 107 mA**（ch5 は typ 68 mA）。アンカーは連続受信なのでここに張り付く。
  外部給電で動かしていた回のデータは、給電が持っていたかを確認するまで採用しないこと。
- 上記の変更はすべて**実機未検証**。ビルド（5 ファーム）とホストテスト
  （`make -C tests all`）が通っただけである。

## 2. 何を作ったか

```
components/
  qm33120w_sdk/   Qorvo ドライバ (vendoring, SPDX 保持)              ← 一次資料。信頼してよい
  uwb_port/       dwt_spi_s / deca_sleep / mutex / GPIO              ← 自作
  uwb_qm33120/    デバイス層 + SS/DS-TWR                              ← M5Stack 由来を大幅に修正
  uwb_math/       対称3x3/2x2の閉形式・LDLᵀ・ブロックコレスキー      ← 新設。一般LU/Jacobiは置かない
  uwb_loc/        測位ソルバ Lv0-Lv3（uwb_math ベースに書き換え済み） ← 上流凍結後は本リポジトリで独立開発
  uwb_ranging/    アンカーテーブル + スケジューラ + パイプライン
  uwb_cfgstore/   NVS 永続化 + シリアルコンソール
  uwb_survey/     MDS(逐次三辺測量) + Gauss-Newton + ゲージ固定       ← uwb_math ベース。leave-one-out棄却・キラリティ入力を追加
firmware/         probe / devtest / twr / soltest / tag / anchor
tests/host/       loc（77+回帰59万） / math（10781） / pipeline（188） / survey（561）
tools/            bench_loc（測位ソルバのマイクロベンチ）
docs/archive/     経緯文書（PROGRESS / REIMPL_PLAN / CRITICAL_REVIEW / SURVEY_* など計8本）
```

**ハード依存は `uwb_port` と `uwb_ranging` のスケジューラ部分の2箇所だけ**に隔離。
測位パイプラインと測量計算はホストで検証できる。**線形代数はすべて `uwb_math` に集約**
されており、一般次元の LU 分解・Jacobi 法などは存在しない（設計根拠:
`docs/archive/MATH_AUDIT_2026-08-21.md`）。

configure（エラーで停止）→ configuretxrf → アンテナ遅延 → setlnapamode で、
`dwt_pll_cal()` / `pgf_cal` / `settemperature` は呼んでいない。`ex_16_pll_cal`
はダイ温度が10℃以上動いたときに `dwt_pll_cal()` を再実行する例。`ex_17_bw_cal`
は「PGcount は工場で室温にて実測する必要がある値。PGcount 0 のままだと帯域
補正は一切走らない」としている。API ガイド p.42-43 は送信電力/PGdly の表に
ついて「Decawave の評価ボードに合わせて選んだ値。他のハードウェア設計では、
送信電力校正作業の一環としてこの値を変更する必要があるかもしれない」と明記
（＝基板ごとの校正が前提）している。SDK 内に ESP32 向けターゲットは無い。

## 7. 落とし穴（踏むと時間を失う）

1. **Qorvo 公式サンプルの `.c` は latin-1。`grep -a` を使うこと**
2. **`UUS_TO_DWT_TIME` は DW1000=65536 / DW3000公式=63898。**
   Qorvo の `*_UUS` 定数は実は実マイクロ秒。そのまま流用すると2.5%ずれる
   → **`docs/GLOSSARY.md`**
3. **ESP-IDF ビルドとホスト `make strict` は警告設定が違う。**
   `uwb_survey.c` が `-Werror=maybe-uninitialized` で落ちた実例あり。
   **新規コンポーネントは必ず `idf.py build` も通すこと**
4. **シェルの cwd が持続する。** `cd firmware/anchor` した後に `cat >> PROGRESS.md` して
   迷子ファイルを作った実例あり。**絶対パスを使うこと**
5. **`sdkconfig` は `.gitignore` 済み。** `sed` で書き換える手順を書いてはいけない。
   `-D SDKCONFIG=build/xxx/sdkconfig` 方式を使う（`GETTING_STARTED.md` に検証済みの手順あり）
6. **`components/uwb_loc/` はもう「上流と byte 一致」ではない。**
   上流 `uwb_localizer` を凍結・最終取り込みした後は、`components/uwb_loc/` は本リポジトリで
   独立して開発する方針に転換済み（2026-08-21）。ESP32-S3 向けの最適化（`uwb_math` ベースの
   スカラー展開など）をソースに直接入れてよい
7. サブエージェントに Web 調査を任せるときは**取得手段を明示的に限定する**
8. **複数セッションが同じファイルを同時に編集していることがある。**
   本セッション中、`components/uwb_survey/src/uwb_survey.c` が別セッションの編集途中で
   一瞬ビルドエラーになる瞬間を観測した。ビルド失敗を見たら即座に「壊れた」と判断せず、
   数分おいて `git diff` / 再ビルドで再確認すること
